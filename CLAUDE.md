# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Travel AI Concierge — a production-quality educational project demonstrating Agentic AI with Langfuse observability. Python 3.12, FastAPI, Streamlit UI, LangGraph, uv for all package management.

## Commands

```bash
make install        # uv sync --all-groups
make env            # copy .env.example → .env if missing
make serve          # uvicorn with auto-reload (port 8000)
make health         # curl /health
make ui             # Streamlit chat UI (port 8501), requires `make serve` running separately

make test           # all tests
make test-unit      # tests/unit only (no infrastructure)
make lint           # ruff check
make format         # ruff format
make typecheck      # mypy
make check          # lint + format-check + typecheck

make langfuse-up          # start local Langfuse stack (postgres/clickhouse/redis/minio/web/worker)
make langfuse-down        # stop it
make langfuse-smoke-test  # create a real trace, print its URL (scripts/smoke_test_langfuse.py)
make chat-smoke-test      # POST /chat over real HTTP against a running `make serve` (scripts/smoke_test_chat.py)
make test-integration     # tests/integration — requires langfuse-up first

make generate-data        # (re)writes data/synthetic/*.json from scripts/generate_data.py
make tools-smoke-test     # call the 3 travel tools directly (scripts/smoke_test_tools.py)
make agent-smoke-test     # compare "simple chatbot" vs "tool-using agent" traces, no server needed
make conversation-smoke-test  # real 3-turn conversation + GET /sessions/{id} (scripts/smoke_test_conversation.py)
make seed-prompts         # create/update system prompt v1 (production) + v2 (staging) in Langfuse
make prompts-smoke-test   # fetch both labels, compare — no server needed (scripts/smoke_test_prompts.py)
make generate-eval-dataset # (re)writes data/evaluation/cases.json from scripts/generate_evaluation_dataset.py
make evaluate             # run the deterministic evaluation suite + trajectory report (scripts/run_evaluation.py)
make eval-baseline        # record this run's metrics as the regression baseline (data/evaluation/baseline.json, Milestone 17)
make eval-ci              # same, exits 1 if a case crashed OR a metric regressed past its threshold vs. the baseline (Milestone 17)
make sync-eval-dataset    # publish/update the same cases as a real Langfuse Dataset (scripts/sync_eval_dataset.py)
make experiment-prompt-v1 # run it as a Langfuse experiment, PROMPT_LABEL=production (scripts/run_experiment.py)
make experiment-prompt-v2 # same, PROMPT_LABEL=staging — compare via the printed dataset_run_url
make evaluate-judged      # same as `evaluate`, plus LLM-as-judge scores (Settings.judge_provider, default "fake")
make cost-latency-experiment  # single-step vs multi-step agent: quality, p50/p95 latency, tokens, cost (scripts/run_cost_latency_experiment.py)
make fault-injection-lab  # inject each spec fault type, observe traces, verify graceful degradation (scripts/fault_injection_lab.py)
```

`TRAVEL_SEARCH_PROVIDER=travel_ai_search_api TRAVEL_AI_SEARCH_BASE_URL=http://<host>:<port>` switches the travel tools to a separately running Travel AI Search backend instead of the local synthetic dataset (Milestone 18) — no code change, same `Settings`-driven pattern as `LLM_PROVIDER=anthropic`. `make test-integration` exercises this against a real, locally self-hosted fake server (`tests/integration/test_travel_ai_search_provider.py`) — no external service or credential needed.

`run_experiment.py`/`run_evaluation.py` both also accept `--with-judge` directly (Milestone 11), not just via the `evaluate-judged` Makefile target.

Run a single test file:

```bash
uv run pytest tests/unit/test_health.py -v
```

## Package structure

Source lives in `src/travel_ai_concierge/` (src layout, installed as editable). Key modules:

- `config/settings.py` — `Settings` via Pydantic Settings; `get_settings()` is lru_cache'd. Override with env vars or `.env`.
- `api/app.py` — `create_app()` returns the FastAPI instance; `app` is the module-level singleton used by uvicorn. Flushes the Langfuse client on shutdown if `langfuse_flush_at_shutdown`.
- `api/routes/health.py` — `GET /health`
- `api/routes/chat.py` — `POST /chat`. Opens one root span (`travel_concierge_turn`) per request, sets `session_id`/`user_id`/`environment`/`tags`/`metadata`/`version`/`prompt` via `propagate_attributes(...)` (M6: `tags=["agent"|"direct-llm", "provider:<name>"]`, `version=Settings.agent_version` only on the agent path; M7 adds `metadata.history_turns`; M8 adds `metadata.prompt_version`/`metadata.prompt_fallback` and links the turn's generation(s) to the fetched prompt — see `docs/TRACE_DESIGN.md`). Calls `get_system_prompt()` (M8) for the system message content instead of a hardcoded string. Fetches prior turns from `get_conversation_store()` before building `messages` and replays them as alternating user/assistant messages ahead of the current one (M7); builds the new `Turn` as a local variable so its `turn_id` can be reused in the response, then appends it to the store only after a successful response — a call that raised is never remembered. By default (`Settings.agent_enabled`) delegates to `get_agent_graph().ainvoke(...)`; with `AGENT_ENABLED=false` calls the provider directly instead (the M2 shape, kept intentionally — see `agent_enabled` below). The agent/provider call is wrapped in `try/except`: any exception sets `level="ERROR"`/`status_message` on the root span before re-raising unchanged (M6 — HTTP behavior is still a plain 500). `trace_id` in the response body is `None` unless `Settings.debug`; `client.flush()` is likewise only called in debug mode — never on the unconditional request path (see ADR-004). `message_id` (M12) is always returned regardless of debug — see `conversation/store.py` and `api/routes/feedback.py` below for why it exists as a separate field from `trace_id`. **Gotcha**: with the default `DEBUG=true`, calling `/chat` before `make langfuse-up` costs a measured ~2.5s per request (flush retry/backoff against an unreachable host), not a fast failure — start Langfuse first.
- `api/routes/sessions.py` — `GET /sessions/{session_id}` (M7). Reads `get_conversation_store()`, 404 if the session has no history. `trace_id` per turn is `None` unless `Settings.debug`, same convention as `ChatResponse`; `message_id` (M12) is always populated, same convention too.
- `api/routes/feedback.py` — `POST /feedback` (M12). Resolves `message_id` to a turn via `get_conversation_store().find_turn(session_id, message_id)`, 404 if not found (wrong id, or trimmed out by `Settings.max_history_turns` since it was returned). Calls `client.create_score(name="user_thumbs", value=1.0/0.0, data_type="NUMERIC", trace_id=turn.trace_id, comment=..., score_id=f"feedback-{message_id}")` — **`trace_id` only**, never also `session_id`: Langfuse's ingestion API requires exactly one of `traceId`/`sessionId`/`datasetRunId` per score and rejects (400) a body with more than one — the Python SDK's own signature happily accepts both as kwargs (confirmed via `inspect.getsource`), which is *not* the same guarantee, and `create_score()`/`flush()` never surface the server-side rejection back to the caller (batch export runs on a background thread and only logs it). An earlier version of this route passed both and silently dropped every score — caught live in the browser, not by any test; see `docs/EXPERIMENTS.md`, Milestone 12. `score_id` is deterministic per message so a later comment updates the same score rather than duplicating it — modeled on `create_dataset_item()`'s id-based upsert (M10), but **not independently verified for scores** (this deployment's Langfuse "events_only" mode has no read API — see `docs/langfuse.md`). Flushes only in debug mode, same convention as `chat.py`.
- `api/schemas/chat.py` — `ChatRequest`/`ChatResponse` Pydantic models. `ChatResponse.message_id: str` (M12) is required and always populated, unlike the debug-gated `trace_id`.
- `api/schemas/sessions.py` — `SessionTurn`/`SessionResponse` Pydantic models (M7). `SessionTurn.message_id: str` (M12), same always-populated convention.
- `api/schemas/feedback.py` — `FeedbackRequest` (`session_id`, `message_id`, `thumbs_up: bool`, optional `comment: str`) / `FeedbackResponse` (`recorded: bool = True`) (M12).
- `conversation/store.py` — `ConversationStore` (M7): in-memory `dict[session_id, list[Turn]]` behind an `asyncio.Lock`, `get_history()`/`append_turn(..., max_turns)`. `append_turn` trims to the most recent `max_turns` (oldest dropped first) — **not** a database; state is per-process and lost on restart, a deliberate choice documented in `docs/architecture.md`'s "Conversation Memory" section, not an oversight. `Turn` gained `turn_id: str` (M12, `uuid.uuid4().hex`, default-factory generated) and a new `find_turn(session_id, turn_id)` lookup — the mechanism `POST /feedback` uses to resolve a client-visible `message_id` back to the real `trace_id` without ever exposing that trace_id to the client itself.
- `conversation/__init__.py` — `get_conversation_store()`, lru_cache'd. **Unlike every other lru_cache singleton in this codebase, this one is stateful, not just cached config** — tests that hit `/chat` or `/sessions` must clear it (`get_conversation_store.cache_clear()`) in the same fixture that clears `get_settings`/`get_llm_provider`/etc., or a `session_id` reused across two tests will carry real conversation history between them.
- `prompts.py` — `get_system_prompt()` (M8): fetches the system prompt from Langfuse Prompt Management by `Settings.prompt_label` (default `"production"`), `fallback=SYSTEM_PROMPT_FALLBACK` so it never raises. **Gotcha**: `Langfuse.get_prompt()` makes a real, blocking network call on cache miss with retries/backoff by default — `chat.py` calls it unconditionally, so every test that hits `/chat` must monkeypatch `get_system_prompt` (see `_StubPrompt` in `test_chat_route.py`/`test_trace_design.py`/`test_sessions_route.py`), the same offline-by-default pattern as `LLM_PROVIDER=mock`. **Gotcha 2**: fallback prompts (`.is_fallback=True`) are never linked by `propagate_attributes(prompt=...)` — verified against the SDK's own `_extract_propagated_prompt` source, not assumed — so when Langfuse is unreachable, the turn's generation(s) simply have no prompt link, which is correct, not a bug. `scripts/seed_prompts.py` (`make seed-prompts`) creates v1 (`production`) + v2 (`staging`) — safe to re-run, each call creates a new immutable version rather than mutating one.
- `logging_config.py` — structlog, JSON in production, coloured key=value in TTY
- `faults.py` — `FaultInjectingProvider`/`make_failing_tool()` (M15): controllable fault injection, deliberately not a global `Settings` flag (a footgun risk) — explicit wrappers swapped in the same scoped, restored-in-`finally` way `evaluation/cost_latency.py`'s `UsageTrackingProvider` (M14) already established. `FaultInjectingProvider(wrapped, fault=...)`: `llm_timeout`/`llm_provider_unavailable` open their own `llm_call` generation span, mark it `ERROR`, and raise before ever calling the wrapped provider; `llm_malformed_output` calls the real wrapped provider (keeping its own instrumentation correct) then strips a required argument from whatever tool call comes back, reusing `agent/nodes.py`'s already-proven missing-argument handling (M6) rather than inventing a new failure path — this project has no free-form JSON output to corrupt instead. `make_failing_tool(fault, tool_name=...)` returns a function matching `TOOL_REGISTRY`'s calling convention that raises immediately — for temporarily swapping one `TOOL_REGISTRY` entry, not registering permanently. No real tool-timeout mechanism exists to trigger (today's tools are synchronous local JSON lookups with nothing slow to preempt) — `tool_timeout` simulates a tool that detected and raised its own timeout, the realistic shape a real network-backed tool would take.
- `observability/langfuse_client.py` — `get_langfuse_client()`, lru_cache'd, built explicitly from `Settings` (SDK's own env-var auto-discovery won't see `.env` — pydantic-settings doesn't mutate `os.environ`). Always returns a real client, even when `langfuse_enabled=False` (passes `tracing_enabled=False` through) — call sites never need an `if enabled:` branch. **Its `lru_cache` is separate from `get_settings()`'s** — tests that monkeypatch Langfuse-related env vars must clear both caches (`get_settings.cache_clear()` and `get_langfuse_client.cache_clear()`), or they'll silently reuse whichever client config the first test in the run happened to construct.
- `providers/llm/base.py` — `LLMProvider` Protocol (now declares a `model: str` attribute too — needed once `chat.py` reads `provider.model` polymorphically), `Message`/`LLMResponse`/`Usage`/`ToolCall`/`ToolSpec` models. `complete()` takes an optional `tools: list[ToolSpec] | None` (Milestone 5); `Message`/`LLMResponse` carry `tool_calls`.
- `providers/llm/mock.py` — `MockProvider`, deterministic word-count-based token usage, still opens its own `llm_call` generation span (same shape as the real provider). Since M5: a fixed keyword-trigger table (`_MOCK_TOOL_TRIGGERS`) decides whether to "call" a tool — a test double for reasoning, not an attempt at one. Recognizes a `role="tool"` message already in context and synthesizes a final answer from it, so it exercises the full agent loop (both hops), not just the first. **M15**: `_decide()` is now called inside a `try/except` that marks the generation `level="ERROR"` before re-raising — defensive (Mock's own logic can't currently raise), added for consistency with the same fix in `AnthropicProvider` and because `FaultInjectingProvider`'s `llm_malformed_output` fault calls through to whichever real provider is wrapped, Mock included. **M16**: `_MOCK_TOOL_TRIGGERS` only keeps the (still-crude, still-hardcoded-args) `"hotel"` trigger now — a deliberately-injected and then diagnosed-and-fixed regression. A `"trip"` keyword was added to fix a failing eval case (`culture-001`) by copy-pasting the old `"destination"` trigger's shape, and silently made `vague-request-002` ("Help me plan a trip.") call `search_destinations` instead of asking the clarifying question it needed — caught not from the Layer 1 aggregate pass count (which moved in the *improving* direction, 82→83, since the bad trigger fixed one case while breaking another) but from per-case diffing plus a real Langfuse trace showing the `llm_call` generation's decision contradicting the system prompt's own text. Fixed with `_DESTINATION_TRIGGER_WORDS`/`_KNOWN_TAGS`: `"destination"`/`"trip"` now only fire `search_destinations` when the message contains an actual detected interest tag (the same vocabulary `TOOL_SPECS` documents), passing the *detected* tags instead of a hardcoded `["beach"]` — see `docs/EXPERIMENTS.md`, Milestone 16, for the full before/after numbers, and `docs/RATIONALE_PER_MILESTONE.md` for why the bug had to live here rather than in the system prompt (no `ANTHROPIC_API_KEY` in this environment).
- `providers/llm/anthropic_provider.py` — `AnthropicProvider`. The installed `anthropic` SDK's `messages.create()` has **no `temperature` parameter** — verified by introspection, not assumed; `Settings.llm_temperature` is unused here. Since M5: `_to_anthropic_messages()`/`_to_anthropic_tools()` translate our provider-agnostic shapes to Anthropic's real ones (verified via SDK type introspection — `ToolParam`, `ToolUseBlockParam`, `ToolResultBlockParam`). **Anthropic has no "tool" role** — a tool result must be sent as a *user* message containing a `tool_result` content block; getting this wrong would likely fail silently rather than raise. Unverified against the live API in this environment (no `ANTHROPIC_API_KEY`); pinned by 6 offline unit tests (`tests/unit/test_anthropic_translation.py`) plus a skip-by-default integration test that will exercise it for real once a key exists. **M15 fix**: `messages.create(...)` is now wrapped in `try/except`, marking `generation.update(level="ERROR", status_message=str(exc))` before re-raising — previously missing entirely; confirmed by reading Langfuse's own `start_as_current_observation` source (a bare `try/finally`, no `except`) that the SDK never does this on its own, so a real timeout/connection failure left the `llm_call` span unmarked, only the root trace (`chat.py`'s try/except) explained anything. Pinned by `tests/unit/test_anthropic_provider_errors.py` (`InMemorySpanExporter`, `provider._client.messages.create` monkeypatched to raise a real `anthropic.APITimeoutError`).
- `providers/llm/__init__.py` — `get_llm_provider()`, lru_cache'd, selects Mock vs Anthropic from `Settings.llm_provider`.
- `providers/travel_search/base.py` — `TravelSearchProvider` Protocol (M18): `search_destinations`/`search_hotels`/`get_destination_information`, same signatures as the tool functions themselves. **Deliberately synchronous, unlike `LLMProvider`** — `agent/nodes.py`'s `tools_node` calls every `TOOL_REGISTRY` entry as a plain sync call (`func(**call.arguments)`, never awaited), a convention every tool since M4 depends on; making this Protocol async would mean making the whole tool-execution path async too. See ADR-006.
- `providers/travel_search/data.py` — `get_destinations()`/`get_hotels()`, lru_cache'd, load `data/synthetic/*.json`. **Moved here from `tools/data.py` in M18** to break a real circular import (`tools/travel_tools.py` needs `providers.travel_search`; `providers/travel_search/local.py` needed `tools.data`; but importing anything from `tools` first runs `tools/__init__.py`, which eagerly imports `travel_tools.py` — found by running the tests, not anticipated) — also the more honest home for it, since loading the local dataset is now a concern of the *local search provider*, not the tool-wrapping layer. Path resolved via `Path(__file__).resolve().parents[4]` (repo root, one level deeper than the old location) — same pattern as `tests/unit/test_ui_chat.py`'s `APP_PATH`.
- `providers/travel_search/local.py` — `LocalSyntheticTravelSearchProvider` (M18): the always-available default, the exact filtering logic that used to live in `tools/travel_tools.py` directly, moved here unchanged. Opens its own `travel_search_backend` span around the filtering — same "structural trace-shape consistency across providers" reasoning `MockProvider`/`AnthropicProvider` already established for `llm_call` (M2/M5), even though a local, in-process lookup has near-zero latency to report.
- `providers/travel_search/api.py` — `TravelAISearchAPIProvider` (M18): calls a separately running Travel AI Search backend over `httpx2.get(...)` (module-level calls, not a persistent `Client` — matches the one other real outbound HTTP call site in this repo, `ui/streamlit_app.py`'s `httpx2.post(...)`, and stays trivially testable via `monkeypatch.setattr("httpx2.get", ...)`). **The HTTP contract is assumed, not confirmed** — this repo has no access to the real Travel AI Search project; response bodies are validated against this project's own `Destination`/`Hotel` models, so a real mismatch raises a clear error rather than silently accepting malformed data. On any `httpx2.HTTPError` (connection failure, timeout, non-2xx), marks its own `travel_search_backend` span `level="ERROR"` before re-raising — same M15 pattern as `AnthropicProvider`/`MockProvider`'s `llm_call`. A 404 on `get_destination_information` returns `None`, matching the local provider's "not found" convention, not an exception. See ADR-006 and `tests/integration/test_travel_ai_search_provider.py` (a real local HTTP server, not skip-by-default — no paid credential needed).
- `providers/travel_search/__init__.py` — `get_travel_search_provider()`, lru_cache'd, selects Local vs API from `Settings.travel_search_provider` (default `"local"`). Same factory shape as `get_llm_provider()` — must be cleared (`get_travel_search_provider.cache_clear()`) alongside `get_settings`/`get_llm_provider`/`get_langfuse_client`/`get_agent_graph`/`get_conversation_store` in any test or script that varies env vars mid-process; added to `test_trace_design.py`/`test_resilience.py`/`test_chat_route.py`'s `_clear_all_caches()` helpers in M18.
- `domain/models.py` — `Destination`, `Hotel` Pydantic models; `PriceBand` (`"budget"|"mid"|"luxury"`) and `price_band_at_most()` for ceiling-style filtering.
- `tools/travel_tools.py` — `search_destinations`, `search_hotels`, `get_destination_information`. Plain sync functions (nothing to await), each opens its own Langfuse observation with **`as_type="tool"`** — a real, distinct Langfuse type (confirmed by SDK introspection, M1), not just a naming convention. Called standalone (root trace) or, since M5, from `agent/nodes.py`'s `tools_node` (nests under the active trace) — same code either way, no branching on caller. **M18**: each function is now a thin wrapper — opens its own `tool` span (unchanged), then delegates the actual data fetch to `get_travel_search_provider()` (`providers/travel_search/`) instead of calling `tools/data.py` (now moved, see below) directly. `TOOL_SPECS`/`TOOL_REGISTRY`/`agent/nodes.py` needed zero changes — the same "swap the concrete provider, not the call site" pattern `LLMProvider` already proved.
- `tools/specs.py` — `TOOL_SPECS` (JSON Schema `ToolSpec` list, matches Anthropic's `tools` param shape directly) and `TOOL_REGISTRY` (name → callable), both consumed by `agent/nodes.py`.
- `agent/state.py` — `AgentState` TypedDict: `messages: list[Message]`, `iterations: int`. Nodes return whole-list replacements, not `Annotated` reducers — explicit over LangGraph's merge convenience.
- `agent/nodes.py` — `agent_node` (one LLM call with tools offered, `as_type="agent"` span) and `tools_node` (executes every requested tool call inside one `execute_tools` span, catches per-call exceptions so a hallucinated tool call becomes an error message the agent sees, not a 500). **Gotcha**: `agent_node`'s tools-withholding check is `state["iterations"] + 1 >= agent_max_iterations`, not `>=` — tracing the exact call sequence by hand showed the more obvious formula makes that branch unreachable, since routing's own hard cap (in `graph.py`) would always fire one call earlier at the same threshold. See `docs/EXPERIMENTS.md`, Milestone 5, before touching either threshold. **Gotcha (M6)**: a tool call with a missing/malformed required argument raises during `func(**call.arguments)`'s own argument binding — *before* the tool function's own `with` block (and its `tool` observation) ever opens — so `tools_node` is the only place that failure can be recorded at all; it now tracks failed call names and marks `execute_tools` `level="ERROR"` with a `status_message`, in addition to the pre-existing text-based recovery the agent sees.
- `agent/graph.py` — `build_graph()` (hand-wired `StateGraph`, no `langgraph.prebuilt`) and `_route_after_agent()` — the **second**, independent safety net: hard-stops the loop at `agent_max_iterations` regardless of what the last message contains, so a provider that ignores `tools=None` still can't loop forever.
- `agent/__init__.py` — `get_agent_graph()`, lru_cache'd (a compiled graph is stateless and reusable — state travels via `ainvoke()`, never stored on the graph object).
- `evaluation/models.py` — `EvaluationCase` (dataset schema), `CaseResult` (what actually happened), `EvaluatorResult` (pass/fail/**skip** — skip for a check that doesn't apply to a given case, not counted as a failure), `CaseReport` (M9).
- `evaluation/dataset.py` — `load_dataset()`, lru_cache'd, reads `data/evaluation/cases.json`. Same path-resolution pattern as `providers/travel_search/data.py`.
- `evaluation/evaluators.py` — `EVALUATORS` (5 Layer-1/deterministic functions — see module docstring for exactly how each maps to, or deliberately diverges from, the spec's own suggested metric list). Pure functions, no I/O — test with hand-built fixtures (`tests/unit/test_evaluators.py`), not real agent runs.
- `evaluation/runner.py` — `run_case()`: always calls `get_agent_graph()` directly (ignores `Settings.agent_enabled` — evaluation exists to test the agent, so it always exercises that path), also calls `get_system_prompt()`. **Gotcha**: same as `chat.py` — tests must monkeypatch both `travel_ai_concierge.evaluation.runner.get_system_prompt` and `agent/nodes.py`'s `get_llm_provider` to stay offline (`tests/unit/test_evaluation_runner.py` uses scripted fake providers, not MockProvider's real trigger table, so tests assert against known behavior rather than Mock's actual limitations). `run_case()` also takes optional `extra_tags`/`extra_metadata` keyword-only params (M14 follow-up, both default `None`, purely additive — merged into the base `["evaluation", query_class]` tags / `{"case_id", "query_class"}` metadata, not replacing them) — added specifically so `cost_latency.py`'s `run_case_with_metrics(case, config_name=...)` can make its traces filterable by which agent config produced them, after a user asked whether/how the M14 comparison was visible in Langfuse and it turned out not to be. Every other caller (`run_evaluation.py`, `experiment.py`'s `_task`) omits both, unaffected — pinned by `test_run_case_without_extras_behaves_exactly_as_before`, an `InMemorySpanExporter`-based test verifying byte-for-byte identical tagging.
- `evaluation/report.py` — `summarize()`/`to_machine_readable()`/`render_human_readable()`. The human-readable report prints an explicit MockProvider-limitations note whenever `Settings.llm_provider == "mock"` — don't remove this without also fixing the underlying dataset/Mock mismatch it's explaining.
- `evaluation/trajectory.py` — `TrajectoryMetrics`/`compute_trajectory_metrics(case, result)` (M13): `total_tool_calls`, `unique_tools_called`, `missing_tools`, `unnecessary_tools`, `repeated_tools`, `tool_precision`, `tool_recall`, `agent_steps`, plus both directions of clarification correctness (Layer 1's `evaluate_clarification` only checks "clarified when expected"; this adds "did NOT clarify unnecessarily"). Pure function, no I/O, no LLM call — precision/recall computed over the *unique* tool-name set so a correct-but-repeated call doesn't itself hurt either score (`repeated_tools` catches that separately). `tool_precision` is `None` (not `0.0`) when zero tools were called — undefined, not a failure; `tool_recall` is `1.0` when zero tools were expected — nothing could've been missed. **Gotcha**: `MockProvider` can call at most one tool per turn and never repeats one (`providers/llm/mock.py`'s `_decide()` returns after the first trigger match), so `repeated_tools` and `total_tool_calls > 1` are structurally impossible to observe live under Mock — tested with hand-built `CaseResult` fixtures (`tests/unit/test_trajectory.py`), same discipline as `test_evaluators.py`.
- `evaluation/trajectory_report.py` — `TrajectoryCaseReport`, `classify_divergence()`, `final_answer_is_healthy()`, `build_trajectory_reports()`/`summarize_trajectories()`/`render_trajectory_summary()`/`to_machine_readable()` (M13). `FINAL_ANSWER_EVALUATORS = {"response_is_nonempty", "response_references_tool_result"}` — deliberately excludes Layer 1's tool-selection evaluators (`tool_usage_matches_expected`, etc.), which would double-count the same signal already captured by `TrajectoryMetrics`. Classifies each case `aligned` / `good_answer_poor_trajectory` / `poor_answer_good_trajectory`. **Confirmed empirically, not assumed**: across the real 39-case dataset under Mock, `poor_answer_good_trajectory` never occurs (Mock's text is always derived directly from whatever it did, so a correct trajectory and a healthy answer are the same event) — two already-existing cases (`requires-clarification-002`, `impossible-constraint-001`) DO produce `good_answer_poor_trajectory` live, because both happen to contain the keyword `"hotel"` and trigger an unwanted `search_hotels` call; see `docs/EXPERIMENTS.md`, Milestone 13. **M17**: `compute_quality_metrics(reports) -> (quality_pass_rate, trajectory_healthy_rate)` — the two-number pair extracted here (Layer 1 pass/(pass+fail) plus the `is_healthy` rate) so `cost_latency_report.py` (M14) and the new `regression.py` (M17) both reuse the exact same formula instead of each computing it inline; `cost_latency_report.py`'s `compute_config_metrics()` was refactored to call it, output unchanged (verified by its own existing tests, none needed updating).
- `evaluation/langfuse_sync.py` — `sync_dataset()` (M10): publishes `data/evaluation/cases.json` as a real Langfuse Dataset (`DATASET_NAME = "travel-concierge-eval-cases"`), upserting items by each case's own `id`. **Gotcha**: dataset item ids must be unique per Langfuse *project*, not just per dataset — confirmed via a real `409 LangfuseConflictError` while writing the integration test (see `docs/EXPERIMENTS.md`, Milestone 10) — don't reuse a fixed item id across differently-named datasets in tests.
- `evaluation/experiment.py` — `run_named_experiment(run_name=..., dataset_name=DATASET_NAME, with_judge=False)` (M10, `with_judge` M11): wraps Milestone 9's unchanged `run_case()`/`EVALUATORS` for the SDK's `Langfuse.run_experiment()`/`DatasetClient.run_experiment()` API (`langfuse.experiment` module — `TaskFunction`, `EvaluatorFunction`, `Evaluation`, `ExperimentResult`). `_case_from_parts()` maps a dataset item's `input`/`expected_output`/`metadata` back to `EvaluationCase`; `_adapt_evaluator()` maps M9's pass/fail/skip to `Evaluation(value=1.0/0.0)`/no evaluation; `_judge_evaluator()` (M11) does the same for `get_judge_provider().judge(...)`, prefixing each dimension `judge_`. `_trajectory_evaluator()` (M13) does the same for `trajectory.py`'s metrics, prefixing each `trajectory_` — appended to the evaluator list **unconditionally**, unlike `_judge_evaluator` which is only added `if with_judge` — trajectory metrics cost nothing extra (no LLM call), so there's no reason to gate them behind a flag the way a real judge call needs to be. **Gotcha**: `run_experiment` is sync even though the `task` it's given is `async def` — do not `await` it, the SDK manages the task's event loop internally (confirmed by a `TypeError` when tried). Has no offline fallback (unlike prompts) — tested via a real throwaway-dataset integration test (`tests/integration/test_langfuse_dataset_experiment.py`), pure adapter logic tested offline (`tests/unit/test_experiment_adapters.py`).
- `evaluation/cost_latency.py` — `UsageTrackingProvider`/`run_case_with_metrics()`/`MODEL_PRICING`/`estimate_cost_usd()` (M14): purely local cost/latency measurement, built specifically because this deployment's Langfuse "events_only" mode has no read API to pull a cross-run comparison back from — see `docs/langfuse.md`. `UsageTrackingProvider` wraps any real `LLMProvider`, recording `LLMResponse.usage` + wall-clock latency as a side effect; delegates `.complete()` unchanged so the wrapped provider's own Langfuse `llm_call` generation span is unaffected. `run_case_with_metrics()` installs the tracker via a scoped monkey-patch of `agent.nodes.get_llm_provider` — the same import site `test_trace_design.py` already patches — restored in a `finally` immediately after one case, not held across a whole run. Takes an optional `config_name` (M14 follow-up), passed straight through to `run_case()`'s `extra_tags=["cost-latency-experiment", config_name]`/`extra_metadata={"cost_latency_config": config_name}` when given — the mechanism that makes traces from this script filterable in Langfuse by which config produced them. **Gotcha**: `agent/nodes.py` imports `get_llm_provider` without re-exporting it, so mypy flags a direct attribute reassignment as touching an unexported attribute; the two patch/restore lines carry a narrow, documented `# type: ignore[attr-defined]`/`[assignment]` rather than switching to `getattr`/`setattr` (which ruff's B010 flags as no safer than direct assignment — the two linters disagree here, direct assignment + a precise ignore is the resolution). `MODEL_PRICING` keys on a case-insensitive tier substring (`"haiku"`/`"sonnet"`/`"opus"`), explicitly labeled illustrative/unverified against Anthropic's live pricing; `estimate_cost_usd()` returns `None` (not a fabricated `$0.00`) for any unrecognized model, including MockProvider's `"mock-echo-v1"` — confirmed to match Langfuse's own built-in Cost Dashboard, which independently shows the same model at a flat $0.00.
- `evaluation/cost_latency_report.py` — `ConfigMetrics`/`compute_config_metrics()`/`render_cost_latency_comparison()` (M14): aggregates per-case `CaseCostLatency` into p50/p95 latency (`_percentile()`, linear interpolation, numpy's default method, no new dependency), token totals/averages, estimated cost, plus quality reused unchanged from Layer 1's pass rate and M13's `build_trajectory_reports()` trajectory-healthy rate (since M17, via `trajectory_report.py`'s shared `compute_quality_metrics()`, not computed inline anymore) — no new quality metric invented for this milestone. `render_cost_latency_comparison()`'s column width is computed from the actual longest config name (`max(22, ...) + 2`), not a fixed constant — an earlier fixed-width version ran two long config-name columns together with zero separating whitespace on the first real run; see `docs/EXPERIMENTS.md`, Milestone 14.
- `evaluation/regression.py` — `Baseline`/`MetricCheck`/`RegressionCheckResult`/`build_baseline()`/`load_baseline()`/`save_baseline()`/`check_regression()`/`render_regression_report()` (M17): compares `quality_pass_rate`/`trajectory_healthy_rate` (from `compute_quality_metrics()`, the same pairing M14 already computes) against a committed baseline (`data/evaluation/baseline.json`, written only by `make eval-baseline`, never automatically — matches `data/evaluation/cases.json`'s own committed-not-gitignored convention). `check_regression()` is pure logic (no I/O, no `Settings`), tested with hand-built `Baseline` fixtures. Two independent thresholds (`Settings.regression_max_quality_drop`/`regression_max_trajectory_drop`, both default `0.05`), not one blended score — a direct response to M16's finding that the two metrics can move in opposite directions on the same regression; `baseline=None` reports `"no_baseline"`, not a failure, so a fresh checkout with no baseline yet doesn't fail CI. **Gotcha**: the threshold comparison (`delta < -threshold`) carries a `1e-9` epsilon — found by a test asserting the exact boundary (`0.80 - 0.75` in IEEE-754 float is `0.05000000000000004`, not exactly `0.05`), which was failing a strict `<` comparison purely from float representation error.
- `evaluation/judge.py` — `JudgeProvider` Protocol, `FakeJudgeProvider` (default, deterministic — derives scores from M9's own evaluators, e.g. `evaluate_tool_usage`/`evaluate_groundedness_proxy`, never invents a number independently), `AnthropicJudgeProvider` (real, one call per case scoring every applicable dimension at once, `as_type="evaluator"` Langfuse observation), `get_judge_provider()` (lru_cache'd, selects via `Settings.judge_provider`). `_applicable_dimensions()`: `itinerary_coherence` only for `query_class == "itinerary_planning"`, same skip-when-not-applicable principle as M9's evaluators. `_parse_judgments()` raises `JudgeParseError` on malformed/out-of-range JSON — never silently falls back to a placeholder score. **Gotcha**: the judge never sees `EvaluationCase.expected_tools`/`expected_arguments` — only the user message, final response, and raw tool results — so its scores are an independent read of the conversation, not a check against our own test fixtures (that's Layer 1's job). Full documented limitations (not an independent model family, self-preference bias, stochasticity) in this module's own docstring.
- `evaluation/judge_report.py` — `CaseJudgment`, `summarize_judgments()`/`render_judge_summary()`/`to_machine_readable()` — parallels `evaluation/report.py`'s shape but for a 1-5 score distribution instead of pass/fail/skip counts, kept as a separate module rather than merged in.

`ui/streamlit_app.py` (not under `src/` — run via `streamlit run`, not imported as a package) — the Chat UI. Talks to the API only via `httpx2.post(f"{settings.api_base_url}/chat", ...)`, never by importing agent/provider code. Since M7, the sidebar's disclaimer caption reflects real server-side memory (`Settings.max_history_turns`) instead of the old "stateless request" wording — update it again if `max_history_turns`' semantics ever change, since it's read dynamically via `settings.max_history_turns` in the f-string, not hardcoded. **Gotcha 1**: the sidebar debug panel is rendered *before* the `chat_input` handling block in the script's top-to-bottom order, so after a successful exchange the code calls `st.rerun()` before returning — without it, the debug panel would always show the previous turn's trace/model/latency, one interaction behind (`st.session_state` mutations don't retroactively re-render earlier widgets in the same pass). **Gotcha 2**: the sidebar's `get_langfuse_client().get_trace_url(...)` call is wrapped in a broad `except Exception` — verified live (pointed a real server+UI at an unreachable `LANGFUSE_HOST`) that this call raises different exception types depending on failure mode (`httpx2.ConnectError` unreachable, `langfuse.api.commons.errors.UnauthorizedError` bad keys, `httpx2.TimeoutException` slow network); narrower catches would still leak a raw traceback into the UI for the cases not caught. Tested with Streamlit's own `streamlit.testing.v1.AppTest` harness (`tests/unit/test_ui_chat.py`), with `httpx2.post` monkeypatched to stay offline. **M12**: `st.feedback("thumbs", ...)` under each assistant message now `POST`s to `/feedback` with the response's `message_id`, plus an `st.form`-wrapped optional comment box (a form, not a bare `st.text_input`, so the comment only sends on its own submit click, not on every keystroke). `st.feedback` is a *stateful* widget — it keeps returning the same selection on every later rerun, not just the click's own — so a `feedback_submitted` flag in `st.session_state` guards against resubmitting the same rating on an unrelated later rerun (e.g. sending another chat message); see `test_feedback_is_not_resubmitted_on_a_later_unrelated_rerun`. A response with no `message_id` renders no feedback widget at all (nothing to attach it to). **Gotcha 3 (M12)**: a successful "Send comment" click calls `st.rerun()` explicitly, same reasoning as Gotcha 1 — the form's own widgets are drawn earlier in that same script pass, before the click sets `comment_submitted = True`, so without the rerun the form would still render once more (an extra, harmless but confusing render) before disappearing on whatever the next unrelated interaction happened to be; `test_optional_comment_sent_after_feedback_reuses_the_recorded_rating` asserts `len(at.text_input) == 0` right after the click to pin this.

## Architecture

One chat turn → one Langfuse trace. By default (`agent_enabled=True`): `travel_concierge_turn` → `agent` (`as_type="agent"`) → `llm_call` generation, and — only if the model requests a tool — `execute_tools` → the tool's own `as_type="tool"` observation → another `agent`/`llm_call` pair, looping until a final text answer or `agent_max_iterations` is hit. With `AGENT_ENABLED=false`: just `travel_concierge_turn` → `llm_call` (the M2 shape, kept as a live comparison, not deleted). Since Milestone 6, every trace also carries `tags`/`metadata`/(on the agent path) `agent_version`, and the relevant observation gets `level="ERROR"`/`status_message` on failure — see `docs/TRACE_DESIGN.md` for the full taxonomy and a real good-vs-poor example. Since Milestone 7, `messages` sent into that first `llm_call` of a turn already include up to `Settings.max_history_turns` prior exchanges from the same `session_id`, replayed by `chat.py` before the graph/provider is ever called — the agent/graph code itself has no special-casing for this, it just receives a longer `messages` list on later turns. Since Milestone 8, the system message's content comes from `get_system_prompt().compile()` (Langfuse Prompt Management, `Settings.prompt_label`-selected) rather than a hardcoded string, with a local fallback if Langfuse can't serve it. Since Milestone 9, `evaluation/runner.py` runs the same `get_agent_graph()`/`get_system_prompt()` pair against a 39-case local dataset (`make evaluate`) — each case is a real, separately-traced `travel_concierge_turn` tagged `evaluation`, not a parallel code path. Since Milestone 10, that same dataset can also be published to a real Langfuse Dataset and run via the SDK's own `run_experiment()` (`make sync-eval-dataset`, `make experiment-prompt-v1`/`-v2`) — `evaluation/experiment.py` reuses `run_case()`/`EVALUATORS` unchanged, just adapted to the SDK's task/evaluator protocol, so there is exactly one place agent-invocation and scoring logic lives, not two parallel copies. Since Milestone 11, both the local report and the Langfuse experiment can also score cases qualitatively via `--with-judge` (`evaluation/judge.py`'s `JudgeProvider` — fake by default, real Anthropic-backed opt-in), reused through the same two call sites rather than a third pipeline. Since Milestone 12, a real end user can also rate a response — `POST /feedback` sends a genuine `user_thumbs` score (Layer 3), linked to both the trace and the session, resolved server-side from an opaque `message_id` that (unlike `trace_id`) is always returned to the client regardless of `Settings.debug` — see `api/routes/feedback.py` and `conversation/store.py` above. Since Milestone 13, the evaluation pipeline also scores the *path* an agent took, not just the resulting text — `evaluation/trajectory.py`'s metrics and `evaluation/trajectory_report.py`'s `classify_divergence()` are always computed on every `make evaluate` run and always pushed onto every Langfuse experiment run, no extra flag, since (unlike the judge) they cost nothing beyond data `run_case()` already collects. Since Milestone 14, `scripts/run_cost_latency_experiment.py` compares two agent configurations (`AGENT_MAX_ITERATIONS=1` vs the default `5`) on quality/p50-p95-latency/tokens/estimated-cost, measured purely locally via `evaluation/cost_latency.py`'s `UsageTrackingProvider` — necessary because this deployment's Langfuse "events_only" mode has no read API to reconstruct a cross-run comparison from, only the browser UI does. Every case's trace still carries a `cost-latency-experiment` tag plus the specific config name (filterable in Langfuse's Tracing view); `--push-to-langfuse` additionally reuses `run_named_experiment()` (M10) unchanged to give each config a real, natively-comparable `dataset_run_url`. Since Milestone 15, `faults.py`'s `FaultInjectingProvider`/`make_failing_tool()` inject each of the project spec's named failure modes in a controlled, scoped way (`scripts/fault_injection_lab.py`, `make fault-injection-lab`) — tool-layer faults (tool exception, tool timeout, malformed model output) get a real second chance via `tools_node`'s existing recovery (M6) and resolve HTTP 200; LLM-layer faults (timeout, provider unavailable) have no equivalent recovery and resolve HTTP 500, cleanly. This milestone also closed a real gap found by reading the SDK source: `AnthropicProvider`/`MockProvider` now mark their own `llm_call` generation span `level="ERROR"` on failure (previously only the root trace did) — see `docs/DEBUGGING_WORKFLOWS.md` for the full runbook this produced. Since Milestone 16, `docs/EXPERIMENTS.md` and `docs/RATIONALE_PER_MILESTONE.md` walk through a real, deliberately-injected agent regression in `providers/llm/mock.py`'s trigger table (see the bullet above), diagnosed by reading a real Langfuse trace rather than the code, fixed, and re-measured against the full 39-case dataset with `make evaluate` — the aggregate Layer 1 pass count alone moved the wrong way (looked like an improvement) while the bug was live, only per-case diffing and Milestone 13's trajectory metrics caught it. Since Milestone 17, `make eval-ci` is a real regression gate, not just a crashed-case check — it compares `quality_pass_rate`/`trajectory_healthy_rate` against a committed baseline (`data/evaluation/baseline.json`, `make eval-baseline` to update it) and exits non-zero if either drops past its configurable threshold; verified live by reusing Milestone 14's own already-measured "known weaker version" (`AGENT_MAX_ITERATIONS=1`) to make the gate actually fail (exit `1`), then confirming the unmodified code passes clean (exit `0`) — see `docs/EXPERIMENTS.md`, Milestone 17. Since Milestone 18, the three travel tools no longer touch data access directly — `search_destinations`/`search_hotels`/`get_destination_information` delegate to `get_travel_search_provider()` (`providers/travel_search/`), which resolves to `LocalSyntheticTravelSearchProvider` (default, always available) or `TravelAISearchAPIProvider` (a separately running Travel AI Search backend, `TRAVEL_SEARCH_PROVIDER=travel_ai_search_api`) — each opens its own `travel_search_backend` span nested inside the tool span, giving the trace shape `agent → execute_tools → search_hotels → travel_search_backend → agent` the spec's own diagram asks for, verified live against a real local HTTP server standing in for the separate project. See ADR-006. See `docs/architecture.md` for full diagrams, `docs/langfuse.md` for the self-hosted deployment reference, and `docs/decisions/` for ADRs.

LangGraph is the agent framework — a hand-written 2-node (`agent`/`tools`) graph in `agent/`, no `langgraph.prebuilt`. LLM provider is a Protocol (`LLM_PROVIDER` env var) with `MockProvider` (default, offline, deterministic) and `AnthropicProvider` (real); both support tool-calling since M5. Travel tools (M4) are called from the agent's `tools_node` — same unnested-until-called-from-a-trace code as when run standalone. Langfuse is self-hosted via Docker Compose by default (v4 — see `docker-compose.yml`); switch to Cloud by changing `LANGFUSE_HOST` in `.env`.

Langfuse SDK is v4, OTel-based: `Langfuse(...)` construction does no network I/O; spans batch and export on `flush()`/shutdown. Trace-level attributes (`session_id`, `user_id`, `tags`, `environment`) are set via `propagate_attributes(...)` (a module-level import from `langfuse`, not a client method) — there is no `update_current_trace()`. Capture `span.trace_id` while still inside the `with start_as_current_observation(...)` block; `get_current_trace_id()` returns `None` after it exits. `usage_details` dict keys should be `"input"`/`"output"` — verified to render correctly in the UI; the docstring's own example (`prompt_tokens`/`completion_tokens`) is unverified, don't assume it also works.
