# Rationale Per Milestone

Why each milestone was built the way it was — the reasoning that doesn't fit in code comments or the README. See `docs/decisions/` for the more formal ADRs; this document is the narrative connecting them to what actually got built.

---

## Milestone 0 — Scaffolding

**Goal**: a project a developer can clone, install, and run a health check against, with the four foundational architecture decisions made and recorded before any agent or Langfuse code exists.

**What we chose and why**:
- **LangGraph** over transparent Python or CrewAI/AutoGen (ADR-001) — because its graph topology is the observability model: a node maps to a span, a conditional edge maps to a routing decision visible in the trace.
- **Streamlit** over Gradio or React (ADR-002) — the UI is a vehicle for the observability learning objective, not the objective itself.
- **A thin Protocol-based LLM provider abstraction** (ADR-003) — Langfuse instrumentation lives inside each concrete provider, not behind the abstraction, so it stays inspectable rather than becoming magic.
- **Self-hosted Langfuse by default, Cloud via three env vars** (ADR-004) — no-cost, no-credentials path to start learning; Cloud is a configuration change, not a code branch.

Deliberately not built: agent, tools, any actual Langfuse SDK call, LLM providers, UI. Milestone 0 is the skeleton these attach to.

## Milestone 1 — Local Langfuse

**Goal**: prove the observability substrate actually works end-to-end on this machine before building anything that depends on it — a real trace, created by our code, visible in the real UI.

**What we chose and why**:

- **The official self-hosted docker-compose, fetched and verified, not reconstructed from memory.** The project spec explicitly warns against inventing a simplified deployment that drifts from Langfuse's actual requirements. Rather than trust training-data recollection of what the compose file looks like (which turned out to be a major version behind — v3 assumptions, v4 reality), we fetched `github.com/langfuse/langfuse/blob/main/docker-compose.yml` directly and adapted that. This is the same reasoning applied to the SDK: before writing any code against `langfuse` v4.15.1, we introspected the installed package directly (`dir(Langfuse)`, `inspect.signature(...)`) rather than assuming the pre-OTel v2 API most training data would suggest. Both calls paid off — the real API differs from what memory alone would have produced (see the trace_id timing bug caught in `docs/EXPERIMENTS.md`).

- **Headless initialization over manual UI signup as the default** (ADR-005) — reproducibility was already a stated project value (`.env.example`, `make env`); requiring every contributor to click through a signup flow to get working API keys works against that. The manual flow is preserved and documented, not removed.

- **`get_langfuse_client()` builds the client explicitly from `Settings`, not from the SDK's env-var auto-discovery** — pydantic-settings parses `.env` into the `Settings` object without mutating `os.environ`, so the SDK's own `get_client()` would silently see nothing. This keeps the project's single source of configuration truth intact (everything flows through `Settings`) rather than introducing a second, parallel config path that happens to work today.

- **A real client is always returned, never `None`, when Langfuse is disabled** — `tracing_enabled=False` is passed through to the SDK rather than skipping client construction. Call sites never need an `if langfuse_enabled:` branch, which is what "observability must not become a hard runtime dependency" (ADR-004) looks like in practice rather than in principle.

- **Integration tests are marker-excluded by default (`-m "not integration"`), not skipped-by-decorator.** A decorator-based skip (`@pytest.mark.skipif(not langfuse_running())`) would require writing a live-connectivity probe just to decide whether to skip — extra code whose only job is deciding whether to run other code. A pytest marker with a default exclusion filter needs no such probe: `make test` never touches the network, `make test-integration` explicitly opts in.

**Surprises worth carrying forward**: the Langfuse self-hosted stack is now v4 (image registry moved to `docker.langfuse.com`), and its REST API for fetching a trace by ID (`GET /api/public/traces/{id}`) is unavailable in this version's default ingestion mode. Full detail in `docs/EXPERIMENTS.md`. Neither blocks anything in this milestone, but the second one will matter whenever a later milestone (e.g. `make eval-ci`) needs to programmatically verify trace contents rather than just create them.

Deliberately not built: any connection between the agent/API and Langfuse — that's Milestone 2. This milestone only proves the substrate; nothing in the FastAPI app calls `get_langfuse_client()` yet.

## Milestone 2 — Minimal concierge with tracing

**Goal**: a real `POST /chat` endpoint, backed by a real LLM provider abstraction, where every request produces a correctly-shaped Langfuse trace — the first milestone where the agent/API and the observability substrate actually meet.

**What we chose and why**:

- **Introspect the installed `anthropic` SDK before writing `AnthropicProvider`, exactly as Milestone 1 did for `langfuse`.** This paid off again: the installed version's `messages.create()` has no `temperature` parameter at all — a detail no amount of remembering "how the Anthropic API works" would have caught, since it used to have one. `Settings.llm_temperature` stays in the schema (a future provider may use it) but `AnthropicProvider` explicitly doesn't pass it, with a comment explaining why rather than a parameter that silently does nothing.

- **Both `MockProvider` and `AnthropicProvider` open their own Langfuse `generation` span, with identical shape.** This was a deliberate consistency requirement, not just "both happen to use Langfuse": ADR-003 already committed to instrumentation living inside each provider rather than behind the Protocol, and the payoff is that a trace produced while iterating offline against the mock looks structurally identical to one produced against the real model — same span name (`llm_call`), same `usage_details` key convention (`input`/`output`, matching what Milestone 1 already verified renders correctly in the UI). A developer learning to read traces doesn't have to learn two different shapes depending on which provider happens to be configured.

- **`user_id` is never fabricated when absent from a request.** The alternative — generating a synthetic ID per anonymous request — would actively work against the reason `user_id` exists in Langfuse: aggregating cost/behavior for the *same* identity across time. A fabricated one-shot ID pollutes that aggregation with noise. Leaving it unset when the caller doesn't provide one is the more honest choice, even though it means some traces simply have no user attribution.

- **`trace_id` is only returned to the client when `Settings.debug` is true**, matching the project spec's explicit guidance ("desirable in development... do not necessarily expose it in a real production client"). This reused an existing pattern already established for `/docs` and `/redoc` in Milestone 0 rather than inventing a new one.

- **`client.flush()` is called conditionally on `debug`, never unconditionally.** Spans batch and export asynchronously by design (Milestone 1) — forcing a synchronous flush on every production request would reintroduce exactly the hard dependency on Langfuse's availability that ADR-004 rules out. In debug mode, the trade favors immediate visibility over the (here, negligible) latency cost, because the whole point of debug mode is a developer watching the trace appear right after the request returns.

- **A second smoke-test script, hitting the running server over real HTTP** (`scripts/smoke_test_chat.py`), rather than only relying on FastAPI's in-process `TestClient` in the automated tests. `TestClient` proves the route logic works; it doesn't prove request routing, real JSON serialization over a socket, or that `make serve` actually starts something reachable. Both are worth having, for different reasons — see `docs/EXPERIMENTS.md` for how this caught nothing wrong here, but the Milestone 1 equivalent caught a real bug, so the pattern is now a habit.

**Surprises worth carrying forward**: writing this milestone's tests surfaced a real caching bug before it shipped — `get_langfuse_client()` is a separate `lru_cache` singleton from `get_settings()`, and a test fixture clearing only the latter would silently reuse a stale Langfuse client config depending on test execution order. Full detail in `docs/EXPERIMENTS.md`.

Deliberately not built: conversation memory/history across turns (each request is stateless beyond a shared `session_id` label), tools, an actual travel domain, and the LangGraph agent graph itself — all still ahead in Milestones 4–5. `AnthropicProvider` exists and is unit-tested for wiring, but has not been exercised against the real API in this environment (no `ANTHROPIC_API_KEY` configured) — its integration test skips itself cleanly rather than failing.

## Milestone 3 — Chat UI

**Goal**: a real, usable chat interface — multi-turn transcript, session reset, feedback placeholders, an optional debug panel — that talks to the Milestone 2 API exclusively over HTTP, proving the "API and UI remain separate" requirement in code rather than just in an architecture diagram.

**What we chose and why**:

- **Streamlit talks to FastAPI over real HTTP (`httpx2.post` to `Settings.api_base_url`), never by importing agent or provider code.** This was the one hard constraint the project spec named explicitly for this milestone. It also means the UI process and API process can be started, stopped, and even deployed independently — a genuine architectural property, not just a file-organization convention. The cost is exactly what you'd expect: the UI has to handle the API being unreachable as a first-class case (see "displaying errors cleanly" below), the same as any other HTTP client would.

- **`st.feedback("thumbs", ...)` over hand-rolled buttons.** Streamlit ships a widget purpose-built for this ("commonly used in chat and AI apps to allow users to rate responses" — its own docstring). Discovering this by checking the installed Streamlit's actual API (rather than assuming two `st.button` calls was the only option) meant less code, an idiomatic result, and a widget that came with its own `AppTest` test element for free.

- **Feedback is a real, visible interaction with no backend effect yet — deliberately.** The project spec calls this out explicitly as a "placeholder" for Milestone 3; wiring it to an actual Langfuse score is Milestone 12's job, which will need to make real decisions this milestone shouldn't pre-empt (score type, scale, whether to collect a comment). Showing a toast that says exactly that ("not yet sent to Langfuse — see Milestone 12") is more honest than either silently doing nothing or quietly wiring up a half-considered version of M12's actual work.

- **A stable, synthetic `user_id` generated once per Streamlit session, not once per message.** This is the correct way to populate `user_id` in a demo/synthetic context, and it's a different situation from the one Milestone 2 already ruled out: M2 said don't fabricate a *fresh* `user_id` when a single API request omits one, because that pollutes cross-request aggregation with noise. Here, the UI *client* deliberately creates one stable identity for the lifetime of a browser session and reuses it consistently — exactly what `user_id` aggregation is for, and exactly what the project spec asks for ("for synthetic/demo scenarios, generate synthetic users").

- **The debug panel is honest about what it's showing.** "Latency (client-measured)" is explicitly labeled as such, not just "Latency" — it's wall-clock time around the HTTP call from the browser's perspective, not the server-side span duration Langfuse itself records for the request. Conflating the two would be a small but real correctness lie in a project whose entire point is teaching people to read observability data accurately.

- **The debug panel explicitly tells the user this UI's conversations have no LLM memory yet**, rather than letting a multi-turn-looking chat transcript imply capability that doesn't exist. The UI can *display* a full conversation history because it keeps its own client-side list of messages, but every `/chat` call still only sends the latest message (Milestone 2's contract, unchanged) — a real model would have no idea what was said two turns ago. Silently shipping a UI that looks like it remembers, when the backend doesn't yet, would be the kind of "fake complexity" the project spec explicitly warns against — better to say so directly than let a user discover it by being confused.

- **The trace-URL lookup in the debug panel fails silently into a caption, catching broadly (`except Exception`) rather than a specific SDK exception type.** This was added after finding, by actually reproducing it in a browser rather than just reasoning about it, that `get_trace_url()` has more than one realistic failure mode — an unreachable host raises `httpx2.ConnectError`, wrong API keys raise Langfuse's own `UnauthorizedError`, a slow network raises a timeout. All three are variations on the same underlying situation: this is a non-critical debug convenience, and the chat feature it sits next to already works without Langfuse (span creation needs no network). Enumerating exception types one at a time would leave the door open for the next one nobody thought of; the broad catch matches what this code path actually is — an optional nicety degrading, not the application handling a specific anticipated error.

**Surprises worth carrying forward**: writing the `AppTest` for the debug panel's trace link caught a real bug, not just a test-mocking wrinkle — the sidebar renders earlier in the script's top-to-bottom execution than the code that appends a new message, so without an explicit `st.rerun()` after a successful exchange, the debug panel always lagged one interaction behind (showing the *previous* turn's trace/model/latency). A second real bug — a raw traceback rendering in the UI when Langfuse is unreachable — was caught not by the original test suite but by a subsequent documentation review pass that re-ran the actual code path live instead of only re-reading prose; see `docs/EXPERIMENTS.md` for both, including why `st.rerun()` is safe here (it cannot resend the message — `st.chat_input` isn't re-invoked).

Deliberately not built: any actual conversational memory (Milestone 7), real Langfuse score submission for feedback (Milestone 12), and anything travel-domain-specific (Milestone 4) — the UI is a faithful window onto exactly what Milestone 2's API already does, no more.

## Milestone 4 — Synthetic travel tools

**Goal**: real, typed, independently-tested travel tools backed by real (synthetic) data — proven to work and to instrument correctly in Langfuse, before anything wires them into an LLM's decision-making.

**A milestone-boundary question, resolved by reading ahead rather than reading literally**: the project spec's M4 text says "connect them to the agent," but there is no agent yet — LangGraph doesn't exist until Milestone 5. Rather than force a premature wiring decision, I read M5's own spec text for the actual boundary: M5 frames itself as producing the *first* comparison between "simple chatbot" and "tool-using agent" traces. If M4 had already wired tools into `/chat`'s LLM call, that comparison would have nothing new to show in M5 — the tool-using trace would already exist. So M4's real job, consistent with the milestone sequence's own internal logic rather than one ambiguous sentence, is to build and independently verify the tools; M5's job is to make an LLM actually choose to call them. This is the same kind of interpretive call already made for the M2/M3 conversational-memory question — flagging the reasoning here rather than silently picking one reading.

**What we chose and why**:

- **Hand-authored data, not randomly generated, despite the spec calling for "deterministic synthetic data."** At this scale (8 destinations, 18 hotels) a fixed seed buys nothing a human reviewing 26 literal records doesn't already get for free, and hand-authored content reads as real geography rather than obviously-templated Faker output. "Deterministic" is satisfied because running `scripts/generate_data.py` twice produces byte-identical JSON — determinism was never about *how* the values were chosen, only that choosing them again gives the same answer.

- **The generation script is the source of truth; the JSON files are a committed, regenerable artifact.** This mirrors the project's existing bias toward `make`-driven reproducibility (`make langfuse-up`, `make generate-data` now among them) — editing `scripts/generate_data.py` and re-running it is the sanctioned way to change the dataset, not hand-editing JSON that would then disagree with its own generator.

- **`as_type="tool"` instead of a plain `span` named `tool.search_hotels`.** The Langfuse OTel SDK has a first-class `tool` observation type (confirmed by introspection back in Milestone 1, not assumed here) with its own UI filter facet and icon — using it is the difference between a human-readable naming convention and actually telling Langfuse what kind of thing this is. Verified live: the Tracing view's Type facet shows a genuine `TOOL` count alongside `SPAN`/`GENERATION`, not just tool calls with distinctive-looking names.

- **Tool functions are plain, synchronous Python — no `async def`, no dependency on the LLM provider abstraction, no dependency on the API layer.** There is nothing to await (in-memory list filtering over a small JSON-backed dataset); adding `async` where nothing is asynchronous would be exactly the kind of premature-complexity the project spec warns against. This also means the tools have zero coupling to *how* they'll eventually be invoked (native LLM tool-calling vs. a LangGraph node vs. something else) — that decision is now free to be made in Milestone 5 without touching this milestone's code.

- **No tool-schema/JSON-schema representation for LLM consumption yet.** It would be easy to also generate an Anthropic-style `tools` parameter block right now, but that format is a guess at what Milestone 5's actual integration approach wants, made before that approach is chosen. Building it now risks reshaping it later for no benefit today — the tools are fully usable and testable as plain function calls without it.

**Surprises worth carrying forward**: none of substance this milestone — see `docs/EXPERIMENTS.md` for the (uneventful, first-try-correct) verification detail. The one thing worth remembering forward: because each tool only opens its own `start_as_current_observation(...)` block and touches no trace-level state, Milestone 5 should be able to call these functions from inside an active `travel_concierge_turn` trace and see them nest automatically — that nesting is designed in via OTel context propagation, not yet exercised live, since nothing calls these tools from within a live request trace until M5 exists.

Deliberately not built: any connection from `/chat` or the LLM provider to these tools (Milestone 5), tool-selection logic of any kind (heuristic or LLM-driven — both are Milestone 5's job), and a `TravelSearchProvider`/`TravelAISearchAPIProvider` abstraction for a real upstream travel search service (Milestone 18, optional).

## Milestone 5 — Explicit Agentic AI workflow

**Goal**: replace `/chat`'s direct LLM call with a real, hand-written LangGraph agent that can decide to call a tool, execute it, and incorporate the result — the wiring Milestone 4 deliberately deferred.

**A second interpretive call, same spirit as Milestone 4's**: the spec's conceptual diagram draws "understand request," "need clarification?," and "select tool(s)" as three separate boxes. I collapsed all three into one node (`agent`): a single LLM call, with tools offered, where the model's own output — plain text vs. a tool request — *is* the routing decision. Forcing a dedicated classifier call to decide "should I clarify?" before even attempting an answer would duplicate work the model already does in one pass, and isn't what the diagram is actually asking for once you read it as intent (a workflow shape) rather than a literal call count. Flagging this the same way as the M4 boundary call, for the same reason: the interpretation is defensible but not the only possible reading.

**What we chose and why**:

- **A hand-written `agent ↔ tools` loop, verified with a toy LangGraph example before any real node existed.** Two nodes, a conditional edge, an edge back from `tools` to `agent` — this is the standard "ReAct-style" shape, and I confirmed the state-passing mechanics (`TypedDict`, nodes returning whole-list replacements rather than relying on LangGraph's `Annotated` reducer convenience) with a throwaway 6-line example before writing `agent_node`/`tools_node` for real. Consistent with this project's running discipline of checking real APIs empirically (Langfuse in M1, Anthropic in M2, LangGraph here) rather than building against a remembered or assumed shape.

- **`LLMProvider.complete()` gained a `tools` parameter and `Message`/`LLMResponse` gained `tool_calls`, built from Anthropic's actual introspected types** (`ToolParam`, `ToolUseBlockParam`, `ToolResultBlockParam`), not from memory of "how tool-calling APIs usually work." This confirmed something non-obvious: Anthropic has no native "tool" role — a tool result must be sent back as a *user* message containing a `tool_result` content block. Getting this wrong would have been a silent, hard-to-spot bug (the API might accept a malformed history in some cases and misbehave, rather than reject it outright) — verified instead via 6 offline unit tests pinning the exact translated shape.

- **`as_type="agent"` for the reasoning node, `as_type="span"` for the tool-execution-batch grouping node.** Same principle Milestone 4 established for `tool`: use Langfuse's real distinct type for the thing that IS one (a reasoning/decision step), and the generic type for a step that's genuinely just coordination (grouping N tool calls from one turn). Verified live: `AGENT` appears as a real, distinct value in Langfuse's own Type filter facet, not just descriptive naming.

- **`MockProvider` gained a small, fixed keyword-trigger table to decide when to "call" a tool.** This is a test double standing in for reasoning, not an attempt at one — its only job is letting the full agent loop be exercised deterministically offline, matching the project's established testing philosophy (no paid API required for `make test`). It also recognizes "I already have a tool result in context" and synthesizes a final answer from it, so the mock exercises the *entire* loop shape (both hops), not just the first.

- **Two independent safety nets against an infinite tool-calling loop, not one.** `agent_node` withholds tools once about to make the last allowed call (so a well-behaved provider naturally produces a clean final answer instead of an empty-content dead end), and `_route_after_agent` separately hard-stops once the iteration cap is reached regardless of what the last message contains (so a provider that ignores `tools=None` — a real possibility for any future non-Anthropic provider — still can't loop forever). Building only the first would leave a genuine production risk (unbounded cost/latency from a misbehaving model); building only the second would produce technically-safe but user-visibly-broken empty responses at the cap. This dual design, and a real off-by-one bug in it, was caught by hand-tracing the exact call sequence for a small `max_iterations` *before* running anything — not by a failing test. Full detail in `docs/EXPERIMENTS.md`.

- **`Settings.agent_enabled` (default `True`) as a one-line way to get the exact comparison the milestone spec asks for** ("compare traces from: simple chatbot, tool-using agent") — flipping it makes `/chat` behave exactly like Milestone 2's direct call, same endpoint, same provider config, no separate code path to maintain in parallel. `scripts/smoke_test_agent.py` demonstrates both shapes in one run without needing to restart the server (a client can't toggle a running server's own env var per-request, so the script calls both code paths directly in-process instead).

**Surprises worth carrying forward**: the max-iterations off-by-one above is the significant one — full detail in `docs/EXPERIMENTS.md`, including the two purpose-built fake providers (one that ignores `tools=None`, one that respects it) used to pin both safety nets independently rather than trusting that a single passing test meant both mechanisms worked.

Deliberately not built: real tool-selection reasoning in the mock path (a fixed trigger table, not a planner — real reasoning is `AnthropicProvider`'s job, unverified live in this environment for lack of an API key), conversational memory across separate `/chat` calls (still Milestone 7), and any Langfuse Prompt Management for `SYSTEM_PROMPT` (Milestone 8) despite it now needing to mention tool use.

## Milestone 6 — Production-like trace design

**Goal**: the spec names eight specific taxonomy items — consistent names, metadata, tags, environment, application version, feature flags, agent version, error metadata — plus documenting the taxonomy and showing good vs. poor trace design. Of those eight, three already existed from earlier milestones (consistent names since M1, environment since M2, application version — `release` — since M1); this milestone adds the remaining five and writes down the taxonomy as a first-class document rather than leaving it implicit across five milestones of code.

**What we chose and why**:

- **`version` is a second, independent axis from `release`, not a synonym for it.** Before writing any code, I introspected `propagate_attributes`'s own docstring rather than guessing at the distinction, and it states the intended use directly: *"Version identifier for parts of your application that are independently versioned, e.g. agents."* That's a literal match for what the milestone spec calls "application version" vs. "agent version" as two separate items — `Settings.app_version` stays the client-level `release` (set once, M1), and a new `Settings.agent_version` is propagated per-trace only on the agent path, since the direct-LLM path isn't running agent code at all and has nothing to version.

- **`agent_enabled` becomes both a tag and metadata, not just a Settings flag.** It already existed since M5 as a Python-level branch; this milestone is the first time its value is actually recorded *on the trace itself*. Tag (`"agent"`/`"direct-llm"`) because it's exactly the kind of coarse, binary segment you'd filter the whole trace list by; also in `metadata` alongside `llm_provider`, since metadata is the right place for structured facts you want visible once you're already looking at one trace, distinct from tags' job of bucketing many traces.

- **Error metadata went where the failure actually happens, not where it's caught.** The original design already had `tools_node` catching every tool-call exception and turning it into text the agent could recover from — correct application behavior, but the resulting `execute_tools` span carried no `level`/`status_message` at all. Worse, tracing through the actual call path revealed a case invisible at *any* observation level: a tool call with a missing required argument fails during Python's own `func(**call.arguments)` argument binding, which happens *before* the tool function's own `with` block — and its `tool`-type observation — ever opens. `search_hotels`'s own span never has a chance to record that failure, because it never opens. The fix lives in `tools_node`: track which calls failed (unknown-tool and argument-binding failures both included) and set `level="ERROR"` with a `status_message` naming them on the one observation (`execute_tools`) that's guaranteed to be open regardless of which failure mode occurred. `chat.py` got the same treatment at the trace root, for any exception the agent loop itself doesn't already turn into a graceful message.

- **Verified fully offline, against the real SDK, not a hand-rolled fake.** Testing "did the right Langfuse attributes get set" without either a live Langfuse instance or trusting the code by inspection alone led to introspecting `langfuse._client.attributes` for the actual OTel attribute keys (`langfuse.trace.tags`, `langfuse.trace.metadata.*`, `langfuse.version`, `langfuse.observation.level`), then constructing a real (non-mocked) `Langfuse` client with `span_exporter=InMemorySpanExporter()` — no network call, but the exact same attribute-setting code path production uses. `LangfuseResourceManager` turned out to be a singleton keyed by `public_key` (confirmed by reading its `__new__`), so each test uses its own unique throwaway key to get a fresh in-memory exporter rather than reusing another test's. Full detail, including a one-off experiment script that surfaced this, in `docs/EXPERIMENTS.md`.

**Surprises worth carrying forward**: this environment's self-hosted Langfuse deployment runs in v4 "events_only" mode, which disables the trace-read REST API entirely (`GET /api/public/traces/{id}` returns a 501-style message naming this explicitly) — and the sandboxed browser pane in this environment cannot reach the host's `localhost`, so the usual "verify live via curl + browser screenshot" step from M1–M5 wasn't available here. The in-memory-exporter tests are a strictly stronger form of verification for the attribute-setting logic itself (they assert on the literal wire-format attributes, not a UI rendering of them), but they don't confirm how Langfuse's own UI displays a `version` set via `propagate_attributes` versus one set via `release` — that visual distinction is worth checking manually (see the Milestone 6 report for what to look at).

Deliberately not built: a general-purpose feature-flag *system* (a flags table, remote config, per-user targeting) — `agent_enabled` is this project's only real flag today, and building infrastructure for flags that don't exist yet would be speculative. The taxonomy in `docs/TRACE_DESIGN.md` documents the pattern so a second flag, when one is actually needed, has an established place to go.

## Milestone 7 — Sessions and multi-turn analysis

**Goal**: the spec asks for "durable or semi-durable conversational state appropriate for the educational system," multi-turn evaluation examples, and the ability to analyse cost/token-growth/repeated-tools/latency/context-accumulation across a conversation. Going in, the gap was concrete and already flagged by name in this project's own docs: `session_id` has grouped traces in Langfuse since Milestone 2, but the LLM itself never saw a prior turn — every `/chat` call built `[system, user]` from scratch. The Streamlit UI's own sidebar said this outright ("the LLM does not yet see earlier turns").

**A scoping call, disclosed like M4/M5's**: the spec's five "Analyse" bullets (cost per conversation, token growth, repeated tools, total latency, context accumulation) read as analysis *questions to be able to answer*, not five features to build. Langfuse's own Sessions view already aggregates cost/latency/tokens per `session_id` — the FastAPI/Sessions sections of the spec explicitly warn against "manually duplicating functionality already handled correctly by the SDK." So this milestone's actual work was giving the agent real memory (the prerequisite for any of those five questions being interesting at all — a session with one turn has no growth to observe) plus one direct, cheap addition (`metadata.history_turns` per trace) rather than a custom analytics endpoint Langfuse already provides.

**What we chose and why**:

- **In-memory, not a database.** "Semi-durable... appropriate for the educational system" is read here as license to add a `dict[session_id, list[Turn]]` behind an `asyncio.Lock`, not Postgres/Redis. Nothing else in this project has a database; adding one just for conversation memory would be exactly the kind of infrastructure-before-need this project's minimalism elsewhere argues against. The honest cost, documented rather than hidden: state is per-process and gone on restart, and a real multi-worker production deployment would need shared storage instead — Langfuse's own trace history remains the durable record of what actually happened, regardless of what this store remembers.

- **History is replayed as clean `[user, assistant]` pairs, not the full internal agent scratchpad.** A turn's tool-calling round trip (`tool_calls`, `role="tool"` messages) is an implementation detail of producing *that turn's* final answer, not part of the conversation transcript — replaying it into a later turn would also risk violating Anthropic's tool_use/tool_result adjacency requirements across a turn boundary neither Anthropic nor this app's own translation layer was designed to span. Storing only the final exchange per turn (`Turn.user_message`, `Turn.assistant_message`) sidesteps that entirely, at the cost of the replayed history not containing which tools were used to produce a past answer — an acceptable trade for conversational continuity, not something the agent's own tool selection reasoning depends on.

- **`Settings.max_history_turns` (default 10), not unbounded replay.** This is the milestone's own "did context size grow excessively?" question, answered as a real bound rather than left as an observation to make after the fact. `ConversationStore.append_turn` trims the oldest turns first once a session exceeds the limit — a session that runs forever costs a bounded, predictable amount of context per turn, not a linearly growing one.

- **`GET /sessions/{session_id}` is deliberately a different thing from Langfuse's own Session view**, not a thin proxy for it — it returns this app's own stored conversation content (for a client that wants to display or restore a conversation, e.g. after a page reload, without a Langfuse API key), while cost/latency/token analysis stays exactly where the spec says it belongs: Langfuse's native per-session aggregation. Two different questions ("what was said" vs. "how much did it cost"), two different, non-overlapping mechanisms answering them.

- **A failed turn is never remembered.** `chat.py` only calls `store.append_turn(...)` after the try/except around the agent/provider call succeeds — an exception propagates out before that line is ever reached. This matters for the same reason M6's error-metadata work mattered: a turn that failed shouldn't silently poison every later turn's context with a broken or partial exchange.

**Surprises worth carrying forward**: none this time in the sense of a bug caught mid-build — the design questions (in-memory vs. database, full scratchpad vs. clean pairs, bounded vs. unbounded) were resolved before writing code, informed directly by this milestone's own spec wording and the "avoid duplicating the SDK" guidance from earlier in the spec. The one thing worth naming: `MockProvider`'s `_decide()` needed no changes at all to support multi-turn history — it already only ever looked at the *last* user message, so a longer `messages` list upstream was invisible to it by construction. That's a quieter version of the same "nesting composes for free" property M4/M5 found with Langfuse spans — this time for message-list length instead of trace structure.

Deliberately not built: the UI does not fetch `GET /sessions/{id}` to restore history on load — its own client-side `st.session_state.messages` already displays the transcript, and adding a redundant network round trip per rerender for data the UI isn't missing would be scope beyond what this milestone needs. Multi-turn *evaluation* examples (test cases that specifically exercise conversation memory) are deferred to Milestone 9, which is where this project's evaluation framework as a whole begins.

## Milestone 8 — Prompt management

**Goal**: move the system prompt out of a hardcoded Python string and into Langfuse Prompt Management — named, versioned, labeled (`production`/`staging`), with a local fallback so the app is never hostage to Langfuse's availability, plus a v1-vs-v2 comparison. Only one real prompt exists to move: the spec's "candidate prompts" list also names travel-preference-extraction, destination-comparison, and itinerary-generation prompts, but this agent doesn't have separate reasoning stages for those (M5's own collapsed-node decision) — there's nothing to migrate that doesn't already live as one system prompt.

**A test-speed risk found before writing any application code**: `Langfuse.get_prompt()` makes a genuine blocking network call on a cache miss, with retries and exponential backoff by default. If `/chat` called it unconditionally, every one of the 78 existing offline unit tests would suddenly depend on live Langfuse infrastructure — exactly the regression this project's "tests must be offline" rule (CLAUDE.md) exists to prevent. This was caught by reasoning through the design *before* wiring `get_system_prompt()` into `chat.py`, not by watching the suite suddenly take 80+ seconds.

**What we chose and why**:

- **`Settings.prompt_label` is the entire v1-vs-v2 comparison mechanism**, not a second hardcoded string behind a flag. Flip `PROMPT_LABEL=staging` and `/chat` uses v2 with zero code change — identical in spirit to `agent_enabled`/`llm_provider`'s existing pattern, and it's the literal mechanism Langfuse's own labeling feature exists for (confirmed via `get_prompt()`'s docstring: no label or version specified → the `production` label is returned by default).

- **`fallback=SYSTEM_PROMPT_FALLBACK` is the whole "don't make the app unable to start" story**, and it costs nothing extra to implement — it's a single keyword argument the SDK already supports, verified by introspecting `get_prompt()`'s source rather than assumed: on any fetch error, with a fallback provided, the SDK returns a synthetic `PromptClient` (`.is_fallback=True`) instead of raising. The fallback text is exactly v1's own content, so the app behaves identically whether or not Langfuse happens to be reachable at that moment — not a degraded experience, a transparent one.

- **Existing tests keep the mock-provider pattern's exact shape: monkeypatch the fetch, don't hit the network.** `_client()`/`_chat_test_client()` helpers across `test_chat_route.py`/`test_trace_design.py`/`test_sessions_route.py` now monkeypatch `get_system_prompt` to a small stub by default, the same way `LLM_PROVIDER=mock` already keeps every test off the real Anthropic API. The *dedicated* prompt tests (`test_prompts.py`) intentionally don't take this shortcut — they point a real, non-mocked `Langfuse` client at `http://localhost:1` (instant connection-refused, no timeout wait) to verify the actual fallback/label/linking behavior end-to-end, same "verify against the real SDK" discipline `test_trace_design.py` established in M6. A test-only `Langfuse` subclass forces `max_retries=0` on that unreachable client specifically, cutting those 3 tests from ~2.9s to ~0.02s without touching `get_system_prompt()`'s production signature (which deliberately keeps the SDK's real retry defaults — a genuine transient blip *should* retry in production).

- **A real, previously-unknown SDK behavior found while writing the prompt-linking test, not assumed from the docstring's prose alone**: reading `propagate_attributes`'s actual propagation source (`_extract_propagated_prompt`) turned up an explicit rule the docstring only hints at — "Fallback prompts are never linked." A first version of the linking test used the fallback-triggering client and failed with no `prompt.name`/`prompt.version` attributes on the generation at all; tracing that down to the SDK's own source (not assuming a bug in our code) confirmed this is deliberate: linking a generation to "version 0" of a prompt that was never actually served would misrepresent what happened. This directly affects our own production behavior — when Langfuse is unreachable, `chat.py`'s `propagate_attributes(prompt=prompt)` call silently produces no link for that turn, which is correct, not a bug, and is now pinned by a dedicated test rather than left as an implicit assumption.

- **v2's content is a genuinely different instruction, not a cosmetic reword** — it requires tool use for destination/hotel facts instead of merely encouraging it, directly targeting the spec's own "tool-selection accuracy" comparison criterion. Honestly documented alongside it: `MockProvider` never reads the system prompt's content at all (`_decide()` only inspects the last *user* message), so `make prompts-smoke-test`'s default run produces identical replies for both versions — proof the retrieval/labeling/fallback/linking *mechanism* works, not that v2 behaves differently. That comparison needs a real provider, which is why `tests/integration/test_prompt_versions.py` exists as a separate, skip-by-default test requiring both `make seed-prompts` and a real `ANTHROPIC_API_KEY`.

- **Deliberately not declaring a winner.** The spec is explicit: "Do not declare a prompt superior based on a few manually inspected examples." `tests/integration/test_prompt_versions.py` only asserts the two versions are genuinely distinct and each produces a valid completion — never that one is "better." A real comparison (correctness, helpfulness, tool-selection accuracy, groundedness, latency, cost) needs an actual evaluation dataset and repeatable scoring, which is exactly Milestone 9's job, not this one's.

**Surprises worth carrying forward**: two, both caught by testing against the real SDK rather than trusting an assumption — the retry/backoff cost of the fallback path (fixed with a test-only subclass, not a production behavior change), and fallback prompts never being linked (a real, load-bearing SDK rule, now pinned by a test and documented in `chat.py` itself). Also worth noting: creating the same prompt name twice via `create_prompt()` doesn't just apply your requested label — Langfuse automatically also tags the newest version with a system `"latest"` label, visible in `scripts/seed_prompts.py`'s own printed output (`labels=['production', 'latest']`). Harmless here since this app only ever requests `production`/`staging` by name, but worth knowing before assuming a prompt's `labels` list only ever contains what you explicitly passed.

Deliberately not built: prompt *variables* (Langfuse's `{{mustache}}`-style templating) — the current system prompt has no dynamic values to substitute, and inventing one just to demonstrate `.compile(**kwargs)` would be exactly the "fake complexity" the spec warns against. `travel-preference-extraction`/`destination-comparison`/`itinerary-generation` prompts named in the spec's candidate list don't exist as separate prompts, for the reason given in Goal above. Rigorous prompt evaluation (the actual "which is better" question) is Milestone 9+.

## Milestone 9 — Evaluation framework

**Goal**: the first local evaluation framework — a 30-50 case deterministic dataset, deterministic (Layer 1) evaluators, `make evaluate` producing both machine- and human-readable output. The spec is explicit that this milestone does *not* need Langfuse datasets ("do not require Langfuse datasets yet for the core evaluation engine") — that's Milestone 10 — and does not need a regression/CI gate — that's explicitly Milestone 17 ("Establish a baseline... `make eval-ci` with configurable regression thresholds"), even though the Makefile's `eval-ci` target already existed as a placeholder from earlier scaffolding.

**What we chose and why**:

- **The dataset describes what a real agent should do, not what MockProvider actually does.** This was the single biggest design fork, decided before writing a single case: tune the 39 cases to MockProvider's two fixed keyword-triggered behaviors (making the default `make evaluate` run look good), or write genuinely correct expectations grounded in the real synthetic data and let Mock's honest limitations show up as failures. We chose the latter — gaming the dataset to flatter a test double that "is a test double for reasoning, not an attempt at one" (M5's own words) would make the evaluation framework *look* trustworthy while actually measuring nothing real. The report itself prints an explicit note whenever it detects `LLM_PROVIDER=mock`, naming exactly which evaluator categories are expected to fail and why, so a low pass rate reads as informative rather than alarming.

- **A real, undocumented constraint discovered while writing the dataset, not assumed**: `search_hotels`'s `max_price_band` is a *ceiling* (`price_band_at_most` — "includes this band and cheaper"), confirmed by reading `domain/models.py` directly rather than guessing from the parameter name. That makes it well-suited to expressing "budget" queries (ceiling of `budget` = budget only) but structurally unable to express "I want only luxury" (ceiling of `luxury` = any band at all). The "luxury" query-class cases deliberately don't assert a `max_price_band` argument — a well-informed agent aware of this tool's actual semantics would omit the filter and reason over the full returned list instead, and asserting otherwise would have made the dataset wrong, not the agent.

- **Evaluators return pass/fail/*skip*, not just pass/fail.** A case with no expected tool shouldn't have its (nonexistent) tool arguments graded as a failure; a case where clarification isn't expected shouldn't be judged by the clarification heuristic at all. Without a third state, every evaluator would need to run against every case, and "not applicable" would be indistinguishable from "failed" in the aggregate numbers — exactly the kind of misleading signal this milestone is trying to avoid.

- **One evaluator from the spec's own suggested list was deliberately dropped, not just adapted**: "unsupported destination avoided." An early design considered checking whether the final response fabricates a specific destination name when a lookup legitimately returns nothing. But a genuinely helpful agent asked about an unsupported destination might reasonably suggest a real alternative ("I don't have Antarctica, but Reykjavik is a good cold-climate option") — and that check would flag good behavior as a failure. Rather than ship an evaluator with a known false-positive mode, the query class stays in the dataset (for coverage) without a bespoke check; its signal comes from `tool_usage_matches_expected` and the groundedness proxy's natural `skip` when a tool result is legitimately empty.

- **"Response references tool result" is named and documented as a *proxy*, not real groundedness.** It's a plain substring check — does the final text contain a name the tool actually returned — deliberately not dressed up as more than it is. Real groundedness scoring (semantic, not lexical) is Layer 2's job per the spec's own layering, and belongs to Milestone 11's `JudgeProvider`, not this milestone's deterministic layer.

- **Each case is a real Langfuse trace, tagged `evaluation`, not a parallel silent process.** This follows directly from the project's core architectural principle ("Langfuse must NOT be hidden behind a tiny generic logging abstraction") — an evaluation run should be exactly as inspectable as production traffic, not a special code path that happens to skip observability. A failing case can be opened in Langfuse and inspected exactly like a failing real request.

- **Evaluator correctness is tested against scripted fake providers, not MockProvider.** `tests/unit/test_evaluators.py` builds `EvaluationCase`/`CaseResult` fixtures by hand; `tests/unit/test_evaluation_runner.py` monkeypatches `agent/nodes.py`'s `get_llm_provider` with providers that return exactly the tool calls a test wants to assert against (the same `test_agent.py` pattern from M5). This deliberately decouples "does our evaluation code work correctly" (a testable, controllable claim) from "is MockProvider's fixed behavior good" (not a meaningful question — it was never designed to be).

**Surprises worth carrying forward**: the `max_price_band` ceiling semantics above — a real, non-obvious tool constraint that only became visible while trying to write a *correct* expectation for a "luxury" case, not while writing the tool itself. A design smell worth naming for future tool work: a parameter whose real semantics don't match its most natural-sounding use case is worth a second look, or at least an explicit test case exercising exactly that gap (this milestone's `luxury-001`/`luxury-002` cases now do).

Deliberately not built: LLM-as-judge (Layer 2, Milestone 11), human feedback scoring (Layer 3, Milestone 12), any Langfuse dataset synchronization (Milestone 10), and the `--ci` regression/baseline gate (Milestone 17) — `eval-ci` today only fails on a crashed case, explicitly documented as a narrower guarantee than "no quality regression."

## Milestone 10 — Langfuse datasets and experiments

**Goal**: publish the Milestone 9 dataset to a real Langfuse Dataset, run it as a structured, comparable experiment, and demonstrate the spec's own "Experiment A" (prompt v1 vs v2) — the exact comparison Milestone 8's own RATIONALE entry named as needing "a real provider and a real evaluation dataset" to do properly.

**A discovery that reshaped the whole design**: before writing anything, I introspected the installed Langfuse SDK for its dataset API and found `Langfuse.run_experiment()` / `DatasetClient.run_experiment()` — a first-class, purpose-built experiment runner (`langfuse.experiment` module) that handles dataset-item iteration, per-item tracing, dataset-run linking, and score submission automatically, given a `task` function and a list of `evaluators`. This wasn't assumed from memory — verified with a throwaway toy dataset against the real local stack before any real code was written (`create_dataset` → `create_dataset_item` → `get_dataset().run_experiment(...)`), confirming in particular that a Langfuse span opened *inside* the task function nests correctly under the SDK's own dataset-run linking, the same "nesting is free" property this project has relied on since Milestone 4. Finding this changed the plan from "hand-roll dataset-run linking and score submission" to "write two small adapters and reuse Milestone 9 entirely" — a much smaller, safer implementation.

**What we chose and why**:

- **Reuse Milestone 9's evaluators and runner completely unchanged**, via adapters rather than parallel logic. `evaluation/experiment.py`'s `_case_from_parts()` maps a Langfuse dataset item's `input`/`expected_output`/`metadata` back into the exact same `EvaluationCase` Pydantic model M9 already validates cases against; `_adapt_evaluator()` wraps each of M9's five evaluator functions, translating pass/fail/skip into the SDK's `Evaluation` shape. Neither the tool-selection evaluators nor `run_case()`'s agent-invocation logic were touched at all — the risk of a subtle behavioral drift between "the M9 local report" and "the M10 Langfuse-linked run" is zero by construction, not by careful parity-testing.

- **Pass→1.0, fail→0.0, skip→no `Evaluation` emitted at all** (an empty list), not three numeric buckets. This was deliberate so Langfuse's own `ExperimentResult.format()` — which averages numeric evaluation values automatically — produces a meaningful "Average Scores" section without any of our own aggregation code. A case an evaluator doesn't apply to (e.g. checking tool arguments when no tool was expected) contributes no data point at all to that average, rather than silently pulling it down as an implicit zero — the same skip semantics M9 already established, now also honored by an external system we don't control the internals of.

- **Cost, token usage, and latency-per-generation are deliberately not recomputed locally.** The spec's own instruction — "Where supported, rely on Langfuse-native mechanisms. Avoid manually duplicating functionality already handled correctly by the SDK" — applies directly here: Langfuse has captured token usage and cost per generation since Milestone 2, unchanged, and its dataset-run comparison view (`ExperimentResult.dataset_run_url`) already surfaces exactly this aggregated across a run. Building our own equivalent would require plumbing a running usage total through `AgentState` and `agent_node` — a real, non-trivial change to Milestone 5's core state machine — purely to re-derive numbers Langfuse already has. That's out of proportion to what this milestone is actually about (dataset sync + experiment running infrastructure), so quality (via the SDK's own averaging) and latency (cheap, purely local wall-clock timing, no core changes needed) are what we report directly; cost and tokens are "go look at the linked dataset run."

- **Dataset item ids use each case's own `id` (e.g. `"budget-001"`), not a random UUID** — enabling exactly the idempotent-resync property `create_prompt()` gave prompts in Milestone 8 (upsert-by-id, confirmed via the SDK's own docstring: "Upserts if an item with id already exists"). A real, sharp-edged constraint surfaced while testing this, not assumed: dataset item ids must be **unique per Langfuse project, across every dataset in it** — not merely unique within one dataset, as the parameter's own scoping might suggest. Our real dataset's case ids are distinctive enough (`hotel-recommendation-001`, etc.) that this is a non-issue in a single-project local instance, but the integration test hit this directly: a first version used a fixed item id ("hotel-case") with a randomized *dataset* name per test run, and the second run of the exact same test failed with a real 409 `LangfuseConflictError` — the id collided with the leftover item from the first run's (differently-named) dataset. Fixed by suffixing item ids with the same per-run random token as the dataset name, and documented in the test itself so the next person who copies this pattern doesn't rediscover the same 409.

- **The worked comparison is prompt v1 vs v2, not model or agent-config comparison**, even though the spec names all three as things to compare. Prompt comparison is the one axis we can demonstrate *today* without new infrastructure — `Settings.prompt_label` already exists (Milestone 8), and the dataset/evaluator/runner machinery is provider-agnostic already. Model comparison (mock vs. Anthropic) and agent-configuration comparison (agent on/off) use exactly the same `run_named_experiment(run_name=...)` function with a different env var changed first — no new code needed to run those too, just not built as dedicated Makefile targets this milestone, since demonstrating the mechanism once, well, matters more than building three near-identical convenience wrappers around the same function.

**Surprises worth carrying forward**: two real, previously-latent bugs surfaced by simply *using* the new Makefile targets rather than just writing them — (1) `make help`'s target-name filter regex (`[a-zA-Z_-]+`) has excluded digits since it was first written, silently hiding any target with a number in its name from the help output; `experiment-prompt-v1`/`-v2` are the first targets in this Makefile's history to contain one. Fixed by widening the character class to `[a-zA-Z0-9_-]+`. (2) The dataset-item-id global-uniqueness constraint above, caught by the integration test failing on its second run, not by reading documentation carefully enough the first time.

Deliberately not built: automated multi-axis experiment sweeps (model × prompt × agent-config grids) — the spec's Experiments B/C/D/E (model comparison, single-agent vs. planning step, tool description versions, temperature) are illustrative examples spread across this project's later milestones (M11, M14 explicitly), not a checklist for M10 to complete in one pass. Local recomputation of cost/token/latency aggregates, for the reasons given above.

## Milestone 11 — LLM-as-judge

**Goal**: a `JudgeProvider` — deterministic fake plus real configurable — scoring relevance, helpfulness, groundedness, constraint satisfaction, and itinerary coherence, the qualities M9's deterministic Layer 1 evaluators structurally can't assess. The spec is explicit this needs documented methodological limitations, not just an implementation.

**A constraint that shaped the whole design before any code was written**: the spec says "prefer an independent judge model family when possible." This project has exactly one real LLM vendor. Building a second one (OpenAI, still listed as "planned" in the README's own Technology table since Milestone 0) purely to satisfy this one line would be real scope creep — M11 is about the judge mechanism, not about finally shipping multi-vendor support. The honest choice was to build the real judge anyway, using the one vendor available, and document the self-family limitation as loudly as the feature itself, rather than either skip the real judge or quietly pretend the independence requirement was met.

**What we chose and why**:

- **`FakeJudgeProvider` derives its scores from Milestone 9's own evaluators, not arbitrary fixed values.** `relevance` and `helpfulness` read `response_is_nonempty`/`tool_usage_matches_expected`; `groundedness` reads `response_references_tool_result`; `constraint_satisfaction` reads `tool_arguments_satisfy_constraints`. This makes the fake judge genuinely deterministic and testable (not a random-number generator dressed up as a judge), and every rationale it produces says explicitly "Deterministic fake judge... not real language understanding" — the same transparency principle `MockProvider` established in M2 (never let a test double's output be mistaken for something it isn't).

- **One LLM call per case, not one call per dimension.** `AnthropicJudgeProvider.judge()` asks for every applicable dimension's score and rationale in a single structured JSON response. Cost and latency scale with cases, not with cases × dimensions — a real consideration once `--with-judge` is run across all 39 cases with a real key, not a premature optimization.

- **A malformed judge response raises `JudgeParseError`, never silently degrades to a placeholder score.** An earlier instinct was to catch a parse failure and return a neutral "3" so the pipeline never breaks — rejected, because a spec that explicitly says "do not blindly trust LLM-as-judge scores" cannot mean "except when the judge fails to even produce a parseable answer, then trust a made-up 3." A crashed judge call is a signal worth seeing, not a data point worth faking.

- **`as_type="evaluator"`** for the judge's own Langfuse observation — a real, distinct type (confirmed by SDK introspection, same principle `tool`/`agent` established in M4/M5), not a generic span with a descriptive name. The judge call is linked to the case it judged via `metadata.judged_trace_id` rather than true parent-child trace nesting — a deliberate simplicity trade-off (cross-trace parent-span linking is real added complexity for a connection that's already fully answerable by reading the metadata) over a marginal navigation convenience.

- **`itinerary_coherence` is conditional on query class, exactly like M9's evaluator `skip` semantics** — asking a real judge to score a dimension that structurally doesn't apply (there's no itinerary for a "find me a hotel" case) would waste a token budget and produce a meaningless number. Reusing the same "not applicable, don't ask" principle across Layer 1 and Layer 2 keeps the two systems' behavior legible as one coherent design, not two divergent ones that happen to share a codebase.

- **Reused via adapters into both existing evaluation surfaces, not a third parallel pipeline.** `--with-judge` on `run_evaluation.py` (M9's local report) and `run_experiment.py` (M10's Langfuse experiment) both call the exact same `JudgeProvider.judge()` — the same reuse discipline M10 established for M9's own evaluators, applied a second time. There is exactly one place judge-scoring logic lives.

- **The judge sees the conversation, not our own test fixtures.** `_build_judge_user_message()` includes the user's message, the agent's final response, and the raw tool results — deliberately never `EvaluationCase.expected_tools`/`expected_arguments`. Showing the judge our own answer key would turn "constraint satisfaction" into "did the agent match our test data" — which Layer 1 already checks, more cheaply and more reliably. The judge is there to answer a question Layer 1 can't, not to duplicate the question it already answers.

**Surprises worth carrying forward**: none in the sense of a bug found mid-build — the two hardest design questions (how to avoid a fake-but-plausible score on parse failure, how to avoid asking the judge about dimensions that don't apply) were both resolved by directly reusing patterns this project had already established and tested (M9's skip semantics, the "don't silently duplicate the SDK/don't silently duplicate ground truth" discipline running through M8-M10), not discovered by something breaking.

Deliberately not built: a second LLM vendor to make the judge genuinely independent (see Goal above — real scope creep, not this milestone's job); automatic judge-vs-Layer-1 agreement/disagreement analysis (a real, interesting question, but a Milestone 9-evaluation-quality question, not an M11-infrastructure one); human feedback as a third evaluation layer (built next, see Milestone 12 below).

## Milestone 12 — Human feedback

**Goal**: a real end user's thumbs up/down, plus an optional comment, sent to Langfuse as a genuine score — Layer 3 of the evaluation architecture, alongside Layer 1's deterministic evaluators (M9) and Layer 2's LLM-as-judge (M11). Milestone 3 shipped the widget as a visible, honest placeholder; this milestone wires it to a real backend effect.

**A design tension that shaped the whole milestone before any code was written**: `ChatResponse.trace_id` is deliberately hidden outside `Settings.debug` (Milestone 2's own decision, reused as-is here — a production client shouldn't see raw Langfuse trace IDs). But feedback has to work in production, not just in debug mode. Requiring debug mode for feedback to function would quietly break the feature for exactly the deployment mode it matters most in; exposing the raw `trace_id` unconditionally would undo Milestone 2's decision just to make this milestone easier. Neither was acceptable, so this milestone introduces a third option: a new, always-visible identifier that means something different from `trace_id`.

**What we chose and why**:

- **A new opaque `message_id` (`Turn.turn_id`), decoupled from `trace_id`.** `ChatResponse` and `SessionTurn` both now return it unconditionally, regardless of `Settings.debug`. `POST /feedback` takes `message_id`, not `trace_id`, and resolves it back to the real `trace_id` server-side via a new `ConversationStore.find_turn()` lookup — the client never needs to see, store, or send the real trace id at all. This is the direct resolution of the design tension above: `trace_id`'s production-hiding behavior stays exactly as Milestone 2 defined it, and feedback still works everywhere.
- **One `create_score()` call, `trace_id` only — not also `session_id`, despite the Python SDK accepting both.** `inspect.getsource` confirmed the *signature* takes `trace_id` and `session_id` together; it did not confirm the *server* accepts them together, and it doesn't — Langfuse's ingestion API requires exactly one of `traceId`/`sessionId`/`datasetRunId` per score and returns a real `400` otherwise. `create_score()`'s batch export runs on a background thread and only logs that rejection, never raises, so an earlier version of this route that passed both silently dropped every score it "recorded" — found by manually clicking feedback in the live UI and seeing nothing in Langfuse, not by any test (see Surprises below, and `docs/EXPERIMENTS.md`). Dropping `session_id` from the score costs nothing: the scored trace already carries its own `session_id` from when it was created (Milestone 2), so a low-rated response is still findable either per-trace or rolled up per-conversation directly in Langfuse's own UI, with no extra code and no custom "browse low-rated traces" dashboard built for it — consistent with the project's running principle, established since M8, of not duplicating functionality the SDK/UI already handles correctly.
- **A deterministic `score_id` (`feedback-<message_id>`)**, the same id-based-upsert convention `create_dataset_item()` used in Milestone 10, so a comment sent after an initial thumbs click updates that one logical score rather than creating a second, disconnected entry. Unlike M10's dataset-item upsert (which integration tests could actually observe failing on a second run and confirm the fix), this specific behavior for *scores* could not be independently verified here — this deployment runs Langfuse's "events_only" mode, which has no read API at all (see `docs/langfuse.md`). Rather than assert it works, both the route's docstring and this entry say plainly that it's a best-effort assumption, not a confirmed fact — the same honesty discipline M9 applied to evaluator `skip` semantics and M11 applied to its own judge limitations.
- **A comment always attaches to an existing thumbs rating; there is no comment-only submission.** `create_score()` requires a `value`, and a comment with no rating has no natural value to send. Keeping `thumbs_up: bool` required and `comment: str | None` optional avoids inventing a synthetic default rating just to support a flow the spec's own M12 bullet list doesn't ask for.
- **`st.feedback`'s statefulness required an explicit resubmission guard, not just a naive click handler.** Unlike `st.button` (which only reads `True` on the exact rerun of its own click), `st.feedback` keeps returning the same selection on every later rerun — confirmed empirically via `AppTest` before deciding this needed guarding, not assumed from memory of how Streamlit widgets generally behave. Without a `feedback_submitted` flag in `st.session_state`, sending a second, unrelated chat message would silently resend the same rating to `/feedback` on every subsequent rerun. `test_feedback_is_not_resubmitted_on_a_later_unrelated_rerun` pins this directly.
- **The optional comment box is an `st.form`, not a bare `st.text_input`.** A plain text input reruns the script on every keystroke; wrapping it in a form means the comment is only sent on its own explicit submit click, not fragment-by-fragment as the user types.

**Surprises worth carrying forward**: one real bug shipped and was fixed, but not by this project's own automated checks — a real user, clicking thumbs up in the live UI after the milestone was reported "done," found nothing appeared in Langfuse. The cause: `create_score()` was called with both `trace_id` and `session_id`, which the Python SDK's signature happily accepts but Langfuse's ingestion API rejects (exactly one of `traceId`/`sessionId`/`datasetRunId` is allowed). Every prior verification — the unit tests' recording fake, and even the integration test's `create_score()` + `flush()` round trip — passed anyway, because the SDK's batch export runs on a background thread and only *logs* a server-side rejection, it never raises. `inspect.getsource`-style introspection (the project's standard "verify against the real SDK, not memory" discipline, used successfully since M1) checked the wrong layer this time: it confirms what the *client* will accept, not what the *server* will accept, and there's no way to tell those apart without either a real network round trip whose response is actually inspected, or a human looking at the result. The fix: score by `trace_id` only (the trace already carries `session_id` from its own creation, so nothing is lost); the integration test now also posts the same payload shape directly to `/api/public/ingestion` and asserts on the response's own `errors` array, since that's the only place in this "events_only"-mode deployment a rejected write is actually observable. Full detail in `docs/EXPERIMENTS.md`. The same live-testing round also turned up a smaller UX rough edge (not a bug the design got wrong, just a missing `st.rerun()`): the optional-comment form kept rendering for one extra interaction after a successful submit, since its widgets are drawn earlier in that script pass than the click's own state change takes effect — fixed by calling `st.rerun()` right after a successful comment submission, same pattern as the chat response flow, and pinned with `len(at.text_input) == 0` in `test_optional_comment_sent_after_feedback_reuses_the_recorded_rating`. A second, smaller surprise, also a real capability worth remembering rather than a bug: `mcp__Claude_Browser__preview_start` with a project-level `.claude/launch.json` successfully opened a real interactive browser view of the local Streamlit dev server, where an earlier direct-`navigate`-to-`localhost` attempt (Milestone 6) could not reach it.

Deliberately not built: a 1-5 star rating (the project spec's broader Layer 3 section mentions one, but Milestone 12's own scoped bullet list asks only for thumbs + optional comment); a comment-without-a-rating flow (see above); any custom UI for browsing low-rated traces (Langfuse's own trace filtering, e.g. `user_thumbs < 1`, already covers this — same "don't duplicate what the SDK/UI already does" reasoning as the `trace_id`-only scoring decision above).

## Milestone 13 — Agent trajectory evaluation

**Goal**: evaluate the *path* an agent takes — correct tool selection, missing tools, unnecessary tools, repeated tools, excessive steps, clarification correctness — not just the final text, and concretely demonstrate the spec's own two claims: *good answer ≠ good trajectory*, and *poor answer despite reasonable trajectory*.

**A finding that shaped the whole milestone before any new code was written**: before designing anything, I re-ran `make evaluate` against the existing 39-case dataset and read every failure by hand. Two already-existing cases turned out to be live, real instances of "good answer ≠ good trajectory": `requires-clarification-002` (*"I want to book a hotel."*) and `impossible-constraint-001` (*"I want to book a hotel on the Moon."*) both contain the literal keyword `"hotel"`, so `MockProvider` calls `search_hotels` even though neither case expects a tool call or (for the first) explicitly expects a clarifying question instead. The resulting text — `"[mock] Based on the tool result: [...]"` — is non-empty and echoes the tool's raw JSON, so `response_is_nonempty` and the groundedness proxy both pass while `tool_usage_matches_expected` fails. This meant the milestone didn't need new dataset cases to demonstrate the first divergence — it needed a new *lens* on cases that already existed, which is itself worth noting: a 39-case dataset built for Layer 1 pass/fail checks was already carrying trajectory-relevant signal nobody had surfaced yet.

The same read-every-failure pass also confirmed, empirically rather than by assumption, that **no case in the current run ever fails `response_is_nonempty` or the groundedness proxy** — MockProvider's `_decide()` (`providers/llm/mock.py`) can call at most one tool per turn and always derives its final text directly from whatever it just did (echo the message, or echo the tool's own JSON). That makes "poor answer despite reasonable trajectory" structurally impossible to produce live under Mock — confirmed by exhaustively checking the real run's output, not by reading the code and assuming.

**What we chose and why**:

- **Trajectory metrics live in a new module (`trajectory.py`), separate from Layer 1's `evaluators.py`.** Layer 1's own `EVALUATORS` list already mixes two different questions under one flat pass/fail/skip shape: "does the text look okay" (`response_is_nonempty`, groundedness proxy) and "did the agent do the right thing" (`tool_usage_matches_expected`, tool arguments, clarification). The spec's own framing — comparing final-answer evaluation *against* trajectory evaluation — requires telling these apart, which a single merged list structurally can't do. `FINAL_ANSWER_EVALUATORS` in the new `trajectory_report.py` names exactly which two of Layer 1's five evaluators speak to the *text*; everything trajectory-related comes from the new metrics, not from Layer 1's tool-selection checks (reusing those directly would double-count the same signal on both axes of the comparison).
- **Precision/recall over the *unique* tool-name sets, with a separate `repeated_tools` list.** Calling the *right* tool twice doesn't hurt precision or recall (the set is still correct) but is still a real trajectory defect the spec explicitly asks to catch (`repeated_tool_calls`) — folding repeats into precision would hide a distinct failure mode inside a metric that's supposed to measure something else.
- **`tool_precision` is `None`, not `0.0`, when no tool was called at all.** Division by zero isn't the only reason: a case that correctly calls no tool (nothing expected, nothing called) has nothing for precision to measure, and reporting `0.0` would read as a failure when it's actually the desired outcome. `tool_recall` uses the opposite convention — `1.0` when nothing was expected — since recall specifically measures what was *missed*, and nothing can be missed if nothing was expected; this asymmetry is deliberate, not an inconsistency (see the module's own docstring).
- **The two clarification checks reuse `evaluate_clarification`'s exact "?" heuristic, in both directions.** Layer 1 only ever checks "did it clarify when expected" (and `skip`s otherwise, per M9's own skip semantics). Trajectory evaluation adds the missing direction — did it clarify *unnecessarily* when nothing needed asking — using the identical crude proxy rather than inventing a second, different one, so the two checks stay consistent with each other even though both are known-crude ("looks like a question" is not the same as "meaningfully advances the conversation").
- **Wired into `run_named_experiment()` unconditionally, not behind a new `--with-trajectory` flag.** Unlike `--with-judge` (a real LLM call, real cost, opt-in since M11), trajectory metrics are pure functions over data `run_case()`/`_task()` already collect — no added latency, no added cost. Gating it behind a flag would only add friction for zero benefit, so `_trajectory_evaluator` is appended to the evaluator list the same unconditional way the Layer 1 adapters already are; `make evaluate`/`eval-ci`/`evaluate-judged` all print and save a trajectory report automatically, no new Makefile target needed.
- **The "poor answer despite reasonable trajectory" demonstration is a hand-built fixture, explicitly labeled as such, not a claim about the live dataset.** Given the confirmed structural finding above, honestly reporting "this cannot happen under Mock" and then constructing exactly one clean example by hand (`test_poor_answer_good_trajectory_is_a_hand_built_synthetic_example` in `tests/unit/test_trajectory.py`) — a correct, single, non-repeated tool call paired with an empty final response — is more honest than either omitting the demonstration or quietly implying it came from a real run. Same discipline M9 already established: evaluator *logic* is tested with scripted fixtures precisely because MockProvider's fixed behavior was never designed to be a meaningful quality benchmark.

**Surprises worth carrying forward**: the empirical read-before-designing pass (re-running `make evaluate` and reading every failure by hand, before writing a line of the new module) is what actually found the live "good answer ≠ good trajectory" cases — the alternative, designing the metrics first and only checking the dataset afterward, would likely have led to adding new dataset cases to manufacture a demonstration that, it turns out, already existed. Worth remembering as a general habit for the milestones ahead: check what the existing data already shows before assuming new fixtures are needed.

Deliberately not built: any change to `MockProvider` itself to make it capable of repeated/multiple tool calls or a genuinely bad final answer — tempting, since it would let "poor answer despite reasonable trajectory" and non-zero `repeated_tool_calls` show up in a live run instead of only a hand-built fixture, but `MockProvider`'s fixed single-hop behavior is depended on by tests across many earlier milestones (M2 onward) and changing it is real scope creep for a milestone about *evaluating* trajectories, not about making the mock more sophisticated. A live demonstration of both divergence quadrants under a real reasoning model remains possible with `LLM_PROVIDER=anthropic` — not exercised here, the same `ANTHROPIC_API_KEY` gap as every prior milestone. Trajectory metrics as a Langfuse *Score* (like Milestone 12's `user_thumbs`) rather than only an `Evaluation` on experiment runs — the spec frames trajectory evaluation as part of the offline evaluation loop (M9-era `run_case()`), not a per-production-trace score, so this stayed scoped to the evaluation dataset rather than `chat.py`'s live request path.

## Milestone 14 — Cost and latency experiments

**Goal**: compare at least two agent configurations on quality, p50/p95 latency, input/output tokens, and cost, and discuss the resulting quality × latency × cost Pareto trade-off — the spec's own suggested example, "one LLM planning step vs two." This is the spec's own **Experiment C** ("single-agent vs explicit planning step") from its Experiments A-E list — Milestone 10's own RATIONALE entry explicitly earmarked it for "later milestones (M11, M14 explicitly)," so this milestone is that forward reference coming due, not a new idea introduced here.

**A blocker that shaped the whole design before any code was written**: the natural way to "measure latency/tokens/cost" would be to read Langfuse's own per-generation numbers back and aggregate them — Langfuse already captures all of this natively (unchanged since Milestone 2), and the project's standing principle throughout M9-M13 has been "don't duplicate what Langfuse/the SDK already does." But this deployment runs Langfuse v4 "events_only" mode, which disables the public read API entirely (first found in M1, leaned on repeatedly since) — there is no programmatic way to pull a side-by-side comparison table back out of Langfuse in this environment, only to look at it visually, one run at a time, in the browser. Rather than treat this as a dead end, I checked whether the underlying data was available a different way: `LLMResponse.usage` and wall-clock timing around `provider.complete()` are both available *in our own process*, before anything is ever sent to Langfuse at all. This isn't "duplicating Langfuse" — Langfuse's read API was never in the loop to begin with. It's the same reasoning the Streamlit UI's own "Latency (client-measured)" caption used back in Milestone 3: an honest, explicitly-labeled local measurement, not a claim to be reproducing Langfuse's own server-side number.

**What we chose and why**:

- **"One LLM planning step vs two" via `AGENT_MAX_ITERATIONS=1` vs the default `5`, not a new runner.** Verified live before designing anything: with `AGENT_MAX_ITERATIONS=1`, `agent_node`'s existing `forced_final` check (`state["iterations"] + 1 >= settings.agent_max_iterations`, Milestone 5) is already true on the very first call, so the agent is physically incapable of requesting a tool — one LLM call, always. This needs zero changes to `run_case()`/`agent_node()`/the graph — just a `Settings` toggle, exactly the same reuse discipline Milestone 8 established for `PROMPT_LABEL` (production vs staging) and Milestone 10 reused for the same axis. The alternative — building a second runner that calls the provider directly, mirroring `chat.py`'s `AGENT_ENABLED=false` path — would have needed new code to do something the existing agent graph can already express with one env var.
- **`UsageTrackingProvider` wraps the real provider and records usage/latency as a side effect, rather than threading a usage accumulator through `AgentState`.** The alternative — adding `total_input_tokens`/`total_output_tokens` fields to `AgentState` and updating `agent_node` to accumulate them — would touch the core agent state shape every milestone since M5 depends on, for a change this milestone doesn't need permanently: cost/latency measurement is this one script's concern, not something `/chat`'s production path needs to carry forever. A wrapper that intercepts `LLMResponse` in-process, installed only for the duration of one `run_case()` call and restored immediately after (`finally`), keeps the blast radius to exactly one new file plus one narrowly-scoped monkey-patch of `agent.nodes.get_llm_provider` — the same single import site the project's own tests (`test_trace_design.py`) already patch, just done by a script instead of a pytest fixture.
- **Quality reuses Layer 1's pass rate and Milestone 13's trajectory-healthy rate, not a new metric.** The single-step-vs-multi-step axis is exactly what trajectory health is built to notice — a single-step config can never call a tool at all, which `missing_tools` catches directly — so pulling `build_trajectory_reports()` into this comparison is direct reuse, not a coincidence. No new quality logic was written for this milestone at all.
- **Estimated cost is `None` for `MockProvider`, not a fabricated `$0.00`.** `MODEL_PRICING` keys on a case-insensitive substring of the model name (e.g. `"sonnet"`), covering real Anthropic tiers; `"mock-echo-v1"` matches nothing, so cost reports `n/a` rather than a misleading zero that would look like a real, favorable measurement. The pricing table itself is explicitly documented as illustrative/approximate, not independently verified against Anthropic's live pricing page — the same honesty standard M11 already applied to its judge's own limitations.
- **The resulting Langfuse traces originally didn't self-identify which config produced them — fixed as a same-day follow-up, after the user asked whether/how this was visible in Langfuse.** The initial version left `run_case()`'s trace tagging (`["evaluation", case.query_class]`, Milestone 9) completely untouched, reasoning that this script's own local report was the source of truth and touching shared tagging logic for one script's concern wasn't worth it. Live-checking in Langfuse's UI (opening a real trace, its Cost Dashboard) to answer the user's question surfaced that this really did make the comparison invisible from Langfuse's side, not just "not the primary source" — a real gap, not merely a documentation nicety. Fixed by giving `run_case()` two new, additive-only keyword arguments, `extra_tags`/`extra_metadata` (both default `None`, changing nothing for every other existing caller — `run_evaluation.py`, `experiment.py`'s `_task`), and having `run_case_with_metrics(case, config_name=...)` pass `["cost-latency-experiment", config_name]`/`{"cost_latency_config": config_name}` through them. Verified live, not just by the new unit tests: opened a real trace afterward and confirmed both the tag and the metadata field are actually there. `tests/unit/test_evaluation_runner.py` gained two `InMemorySpanExporter`-based tests (the M6 pattern) proving the merge is additive, not replacing, and that omitting the new parameters reproduces the exact prior tagging byte-for-byte.
- **A second, genuinely optional addition — `--push-to-langfuse` — reuses M10's `run_named_experiment()` completely unchanged**, giving each config a real `dataset_run_url` comparable natively side by side in Langfuse's own Experiments UI (verified live: selected both `cost-latency-single-step` and `cost-latency-multi-step-default` as baseline + comparison and saw per-item scores for both configs in the same row, including the M13 trajectory scores riding along automatically since `_trajectory_evaluator` was already wired in unconditionally). Kept opt-in and separate from the default run, for three honest reasons: it requires `make sync-eval-dataset` to have been run first (a precondition the default path has never needed); it re-runs the full 39-case dataset a second time per config through `_task()`'s own unwrapped provider, so it does **not** carry local metrics (no `UsageTrackingProvider` there) — the printed report remains the one authoritative source for quality/latency/token/cost numbers, this path exists purely for native browsing; and it doubles the trace count for anyone who doesn't need or want that.

**Surprises worth carrying forward**: the first real run of the comparison table's renderer produced two config-name columns with zero separating whitespace ("single-step (max_iter=1)multi-step (max_iter=5, default)") — the column width was a fixed constant chosen to look reasonable for short names, and simply wasn't wide enough for the actual (longer, more descriptive) names used once real data flowed through it. Caught immediately by actually running the script against the real 39-case dataset before writing tests, not by guessing at a safe width in advance. Fixed by computing the width from the actual longest name plus a guaranteed gap, and pinned with a regression test using deliberately long names. The real, substantive result from that same first run: multi-step wins meaningfully on quality (+15.9pp Layer 1 pass rate, +38.5pp trajectory health) at a real, measurable cost (2.1x p50 latency, 2.42x tokens per case) — a genuine, honestly-computed Pareto trade-off entirely under `LLM_PROVIDER=mock`, even with cost itself reading `n/a`. A second surprise, from the user rather than a test run: asking "are we even using Langfuse for this, and can I check?" surfaced that the milestone's own initial "deliberately not built" framing around trace tagging had quietly become a real usability gap, not just a documented scope boundary — worth remembering that a limitation reasoned through and written down in RATIONALE is not the same as a limitation a user would find acceptable once they actually go looking for the thing themselves.

Deliberately not built: a live "small model vs larger model" comparison — the spec's **Experiment B**, its other suggested example for this milestone — since it requires `LLM_PROVIDER=anthropic` and no `ANTHROPIC_API_KEY` is configured in this environment, the same recurring gap as every real-provider comparison in this project; the cost-estimation and provider-wrapping machinery is built and unit-tested to support it the moment a key exists (swap `CONFIGS` to two `LLM_MODEL` values instead of two `AGENT_MAX_ITERATIONS` values — no code change needed), just not exercised live here. Experiments D (tool description v1 vs v2) and E (temperature 0 vs higher) remain unbuilt too — not this milestone's scope, and `AnthropicProvider` doesn't even send `temperature` at all (no such SDK parameter — M2's own finding), so E specifically would need that gap closed first. A generic, config-driven CLI (`--config-a`, `--config-b` flags, arbitrary env var lists) — the spec asks to compare "at least two" configurations, not to build a general experiment framework; `CONFIGS` is a small, explicit, easily-edited list at the top of the script instead, in keeping with the project's "don't build for hypothetical future requirements" principle. Recomputing anything Langfuse itself would show for a *single* run (a single trace's own latency, a single generation's own cost) — that's still native to Langfuse and still inspectable in its UI; only the *cross-run, cross-config comparison* needed a local report, precisely because that comparison has no equivalent in what events_only mode can serve back. Threading `UsageTrackingProvider` into `--push-to-langfuse`'s own `run_named_experiment()` path, so that browsable path also carried local metrics — would mean `evaluation/experiment.py`'s `_task()` needing to know about a Milestone-14-specific wrapper, coupling two modules that have stayed cleanly separated since M10; the printed report remains the single source of truth for the actual numbers, `--push-to-langfuse` exists purely for native side-by-side browsing.

## Milestone 15 — Failure and resilience laboratory

**Goal**: controllable fault injection for the spec's named failure modes (LLM timeout, travel provider error, malformed model output, tool timeout, Langfuse unavailable, no search results), verify each is actually visible in Langfuse trace data, verify the application degrades gracefully rather than crashing, and document production debugging workflows.

**A real bug found by reading the SDK source before designing anything, not by guessing**: before building any fault-injection machinery, I traced through the existing error-handling paths to see what was already covered (a lot, it turns out — M6's `tools_node` catches any tool exception, M9's evaluators already treat empty results as valid, M2's `Settings.llm_timeout_seconds` is already wired into `AsyncAnthropic(timeout=...)`). What I found *missing*: `AnthropicProvider.complete()`'s `generation.update(...)` call — the one place `level="ERROR"` would get set on the `llm_call` span itself — sits *after* `await self._client.messages.create(...)`. If that call raises, the span exits via exception and never gets marked. I confirmed this wasn't a misreading by reading Langfuse's own `_start_as_current_otel_span_with_processed_media` source directly: it's a bare `try/finally`, no `except` at all — the SDK does not mark a span `ERROR` on your behalf just because an exception passed through it. Only the *root* trace (via `chat.py`'s own M6-era `try/except`) would show anything went wrong; the specific generation that actually failed would end with no explanation at all. This is exactly the kind of gap "Errors should be visible in observability data" is meant to catch, and it existed since Milestone 2 — nobody had looked at what a *failed* `llm_call` span actually contains until this milestone's own investigation required it.

**What we chose and why**:

- **Fixed the AnthropicProvider/MockProvider gap directly, before building anything else.** Both now wrap their completion call in `try/except`, marking `generation.update(level="ERROR", status_message=str(exc))` before re-raising — the identical pattern `tools_node` already established in M6, applied to the one place it was missing. Verified live, not just by the new unit test: ran a real timeout through `fault_injection_lab.py` and opened the resulting trace — the `llm_call` generation now shows a red **Error** banner with the real message, where before this fix it would have shown nothing.
- **Explicit, scoped fault-injection wrappers — no global `FAULT_INJECTION` setting.** A runtime env var that can make the whole app misbehave is exactly the kind of switch that gets left on by accident in a real deployment. `FaultInjectingProvider`/`make_failing_tool()` are swapped in the same scoped, restored-in-`finally` way M14's `UsageTrackingProvider` already established (`agent.nodes.get_llm_provider`, or one `TOOL_REGISTRY` entry) — something a test or demo script deliberately opts into, never something ambient.
- **Faults are mapped onto the concrete shape they take in *this* architecture, not simulated abstractly.** "Malformed structured response" has no JSON-parsing step to corrupt in this codebase — the only structured output an LLM produces here is a tool call, so that's what gets corrupted (a required argument stripped), reusing M6's already-proven missing-argument handling rather than inventing a new failure path. "Tool timeout" has no execution-preemption mechanism to trigger, because today's tools are synchronous local JSON lookups with nothing slow to preempt — simulated instead as a tool that detects and raises its own timeout, which is the realistic shape a real network-backed tool with a client-side timeout would actually take, not a gap to apologize for.
- **Tool-layer and LLM-layer faults are treated, and documented, as fundamentally different.** Tracing through the agent loop showed something worth stating plainly: a tool failure already gets a *second chance* — `tools_node` turns the exception into a "tool" result message, and the agent's next LLM call produces a real, coherent answer (HTTP 200). An LLM call failing outright has no equivalent second chance, since the LLM is the thing making decisions — it becomes a clean HTTP 500 (the process doesn't hang or crash, no other request is affected, but it's not a *recovered* answer). `docs/DEBUGGING_WORKFLOWS.md` leads with this distinction rather than burying it, and no LLM-call retry logic was added — the spec's own resilience examples don't ask for it, and it's real scope creep on the one code path every milestone depends on.
- **"No search results" and "Langfuse unavailable" needed no new production code at all — only verification.** Both were already handled: tools return `[]` cleanly (M4), and ADR-004's "observability must not be a hard runtime dependency" was already the design intent. What was missing was proof. `fault_injection_lab.py` demonstrates the first by calling `search_hotels` directly with a nonexistent destination (the only way to get a genuinely empty result — `MockProvider`'s trigger table always uses a fixed, real `destination_id`, so it can't be steered into emptiness through the mocked agent loop). The second gets a real, non-negotiable proof: `tests/integration/test_langfuse_unavailable.py` points `LANGFUSE_HOST` at an unreachable local port and confirms `/chat` still returns 200 in under 2 seconds — this is the single most emphasized resilience claim in the spec ("This last case is particularly important"), and it had never actually been tested end-to-end before this milestone, only asserted in ADR-004's own reasoning.
- **`docs/DEBUGGING_WORKFLOWS.md` is built from real lab output, not imagined.** Every trace shape, every `status_message` example, and the HTTP-status table were taken directly from actually running `make fault-injection-lab` against this codebase — the same discipline M13/M14 already established (read the real data before writing the docs that describe it).

**Surprises worth carrying forward**: writing the `/chat`-level resilience test surfaced a second, smaller gap in the *test* infrastructure itself, not the application: `test_trace_design.py`'s existing chat-level tests only ever assert on the root `travel_concierge_turn` span, never on `agent`/`execute_tools`. Tracing through why revealed that `agent/nodes.py` imports `get_langfuse_client` as its own separate module binding — patching `chat.py`'s copy (the established pattern for chat-level tests) leaves child spans landing on the real, differently-configured cached client instead of the test's `InMemorySpanExporter`, invisible to the test entirely rather than failing loudly. This was never a bug in `test_trace_design.py` (it never needed to assert on those spans), but it's a sharp edge worth remembering for any future test that does: patch both `chat.py`'s and `agent.nodes.py`'s `get_langfuse_client` bindings, not just the first one. `tests/unit/test_resilience.py` does this and documents why in its own helper.

Deliberately not built: LLM-call retry/backoff logic (see above — real scope creep on the shared provider-call path, and not something the spec's own resilience examples ask for); a real "travel provider" to fail over *from* for the "use local synthetic provider if configured" fallback — there's only ever been the local synthetic provider in this project so far, that fallback has nowhere to point until Milestone 18 (optional); a generic execution-timeout wrapper for tools — no real blocking I/O exists yet to time out on, and building preemption infrastructure ahead of the need it would serve is exactly the kind of premature abstraction this project avoids; a global fault-injection toggle — deliberately rejected as a production footgun, see above.

## Milestone 16 — Observability-driven debugging exercise

**Goal**: intentionally introduce a realistic agent problem, generate traces, diagnose it using Langfuse (not by reading code), fix it, re-run the same evaluation dataset, and demonstrate measurable improvement.

**The first real design decision: where can an "agent problem" even live in this codebase, given the constraints already established.** The spec's own examples — poor tool description, a prompt causing excessive tool calls, context causing hallucination — are all failures of an LLM's *reasoning*. That reasoning happens in exactly two places in this project: `AnthropicProvider` (real, but needs `ANTHROPIC_API_KEY`, unavailable in this environment since M2) and `MockProvider` (fully offline, but explicitly documented since M1 as "a test double for reasoning, not an attempt at one" — a fixed keyword-trigger table, not a planner). Given the milestone explicitly asks to *generate traces* and *run the same evaluation dataset* — both fully wired for `MockProvider` by default and not reliably reproducible without a paid API key — the honest choice was to inject the bug into the one mechanism that's both fully offline and actually drives tool-selection behavior: the trigger table. This is presented plainly as a deliberate constraint, not a workaround pretending to be the real thing — the *failure shape* (a decision that silently contradicts the system prompt, with no `level=ERROR` anywhere to filter on) and the *diagnostic workflow* (read the trace, not the code) are identical to what a real prompt/tool-description bug produces in a real model; only the mechanism generating the wrong decision differs.

**The bug was designed to be something a real engineer would actually write, not a strawman.** `culture-001` was a genuine, pre-existing failure (`MockProvider` never called `search_destinations` for "I want a trip full of culture..." because neither `"hotel"` nor `"destination"` appears in it). Adding `"trip"` as a new trigger keyword, copy-pasting the existing `"destination"` trigger's shape, is exactly the kind of change someone chasing a specific failing eval case would make — and it works, for that one case. Its side effect (firing on `vague-request-002`, "Help me plan a trip.", which needs a clarifying question and zero tool calls) is the realistic part: a fix verified against the one case it targeted, not against the rest of the dataset.

**What we chose and why**:

- **Diagnosis is trace-first, not aggregate-pass-count-first — and the aggregate number actively misled in this run.** After introducing the bug, `make evaluate`'s own headline number (82 → 83 pass) moved in the *improving* direction, because the new trigger fixed one failure while breaking a different one. Real per-case diffing (`data/evaluation/results/latest.json`, before vs. after) and Milestone 13's trajectory metrics (`average_tool_precision` 0.900 → 0.864, `total_unnecessary_tool_calls` 2 → 3) were what actually surfaced the regression. This is worth stating plainly for Milestone 17, coming next: a regression gate watching only the single aggregate pass-rate number would not have caught this bug at all.
- **The fix addresses the underlying cause (no content signal required to fire), not just the specific symptom.** Simply reverting `"trip"` would have restored `culture-001`'s original failure. Instead, both `"destination"` and `"trip"` now require at least one detected interest tag (`_KNOWN_TAGS`, the same vocabulary `TOOL_SPECS` already documents for `search_destinations`) before firing at all, and the tool call carries the *actually detected* tags instead of a hardcoded `["beach"]`. This is a materially different, and materially more correct, decision rule — not a patch that only works for the two cases examined by hand.
- **Comparison is against the true original baseline, not just the buggy intermediate state.** It would have been easy to declare victory by showing "with bug" → "after fix" and stopping — but that only proves the regression was noticed, not that nothing else moved. Re-running the full 39-case suite against the pre-bug baseline confirmed `vague-request-002` is back to byte-for-byte the same result (not just "no longer failing this one evaluator"), and additionally reported two more pre-existing, previously-failing cases (`destination-recommendation-001`, `couples-holiday-001`) now passing as a direct, honest side effect of replacing the hardcoded tag with real detection — not claimed as this milestone's primary target, but not hidden either.
- **The trace evidence is real, captured live via the browser against this repo's own `make langfuse-up` stack, not written from imagination.** Both the buggy trace (showing `[tool_calls: ['search_destinations']]` for a message the system prompt itself says should be clarified, not acted on) and the fixed trace (showing the plain `agent` → `llm_call` shape with no `execute_tools` at all) were opened and read directly, the same "verified, not assumed" discipline every milestone since M1 has applied to Langfuse SDK internals, applied here to the *application's own* trace output instead.

**Surprises worth carrying forward**: the aggregate-number-hides-a-regression finding is the most important thing this milestone produced, more than the specific bug itself — a well-intentioned fix that improves one visible metric while quietly breaking something else is a completely ordinary way for real production regressions to slip through, and the fact that it happened here on the *first* deliberately-injected bug, without needing to search for a scenario that would produce it, says the risk is structural, not contrived. Directly relevant to Milestone 17's regression-detection work: whatever threshold-based gate gets built there needs to consider more than one number, or needs per-case comparison, to catch this same shape of regression.

Deliberately not built: a live demonstration of the same bug class against `AnthropicProvider` (a real prompt or `TOOL_SPECS` description edit) — would need `ANTHROPIC_API_KEY`, unavailable here, the same recurring gap as every real-provider comparison since M2. The diagnostic workflow and trace shape transfer directly; only the mechanism producing the wrong decision would differ. A permanent "known bad configurations" regression-testing harness — that's explicitly Milestone 17's job (`make eval-ci` with configurable thresholds), not this one; this milestone stayed a one-time, manually-diagnosed exercise reusing existing tooling (`make evaluate`, the Langfuse UI), not a new automated mechanism.

## Milestone 17 — Regression detection

**Goal**: establish a baseline, introduce a known weaker version, run evaluation, and turn `make eval-ci` into a real regression gate with configurable thresholds — demonstrating how AI evaluation could become a CI quality gate.

**The metric design was already decided by Milestone 16, not invented fresh here.** Milestone 16's own closing line named the requirement precisely: *"a regression gate watching only the single aggregate pass-rate number would not have caught this bug at all... needs to consider more than one number."* That ruled out the obvious, simplest design (gate on `overall.pass` alone) before any code was written. The two metrics chosen — `quality_pass_rate` (Layer 1) and `trajectory_healthy_rate` (Milestone 13) — aren't new either: they're exactly the pair Milestone 14 already computes to compare agent configurations (`ConfigMetrics`). Extracting that pairing into a shared `compute_quality_metrics()` (now in `trajectory_report.py`, reused by both `cost_latency_report.py` and the new `regression.py`) rather than writing a third copy of the same two formulas is the same "reuse, don't duplicate" discipline established since M10.

**What we chose and why**:

- **A baseline is a deliberate, committed file (`data/evaluation/baseline.json`), written only by `make eval-baseline`, never automatically.** The alternative — regenerating it silently on every `make evaluate`/`eval-ci` run — would make the gate meaningless: a real regression would just quietly become "the new normal" on the next run instead of failing anything. `make seed-prompts` (Milestone 8) already established this pattern for a different kind of "reference state a human should consciously update"; this reuses the same reasoning, and the same convention `data/evaluation/cases.json` already uses (committed, not gitignored, unlike `data/evaluation/results/`).
- **Two independent thresholds, not one combined score.** `Settings.regression_max_quality_drop`/`regression_max_trajectory_drop` (both default `0.05`, both env-overridable — the same `Settings` pattern every other tunable in this project already uses) are checked separately, and either one regressing fails the gate. A single blended score (e.g. an average) would let a large drop in one metric hide behind an improvement in the other — precisely the shape Milestone 16's real bug took (quality up, trajectory down). Keeping them separate is a direct, structural answer to that finding, not just a description of it.
- **`check_regression()` is pure logic — no I/O, no `Settings` access, no agent run.** It takes a `Baseline` and two numbers and returns a `RegressionCheckResult`; `run_evaluation.py` is the only place that touches the filesystem or `Settings`. This mirrors `evaluators.py`/`trajectory.py`'s own separation of "pure comparison logic" from "the script that wires it up," specifically so the gate's actual decision rule can be tested with hand-built fixtures (`tests/unit/test_regression.py`) instead of needing a real evaluation run for every test case.
- **No baseline yet is `"no_baseline"`, not `"fail"`.** A regression gate that fails a fresh checkout with no baseline recorded would actively punish the first step the spec itself asks for ("establish a baseline" *before* "run evaluation"). `render_regression_report()` prints exactly what to do next (`make eval-baseline`) rather than a bare failure.
- **A tiny epsilon (`1e-9`) guards the threshold comparison against float noise.** Found by a test, not by inspection: `0.80 - 0.75` in IEEE-754 binary floating point is `0.05000000000000004`, not exactly `0.05` — a drop conceptually *at* a `0.05` threshold was failing a strict `<` comparison purely from representation error. `test_drop_exactly_at_threshold_does_not_regress` pins the boundary itself, not just typical cases well away from it.
- **The demonstration reuses Milestone 14's already-measured "known weaker version" (`AGENT_MAX_ITERATIONS=1`) instead of a new contrived one.** It's a real, one-env-var configuration change with real prior numbers on record, not a fabricated scenario built just to make the gate turn red — closer to the actual failure mode a CI gate exists to catch (an accidental bad default or misconfigured deploy) than a manufactured bug would be. Verified live: baseline recorded from the current code, `make eval-ci` passes clean (exit `0`), then the same command with `AGENT_MAX_ITERATIONS=1` set fails loud (exit `1`, confirmed via `echo $?`, not inferred from printed text) with both metrics past threshold. Full output in [docs/EXPERIMENTS.md](EXPERIMENTS.md).

**Surprises worth carrying forward**: the live demonstration regressed *both* metrics together (a single-step agent breaks tool selection thoroughly enough that even the aggregate pass rate drops), which doesn't by itself prove the two-metric design was load-bearing for *this* run — a single-metric gate would have caught this one too. The two-metric design earns its keep on Milestone 16's actual regression shape (quality up, trajectory down), which is why `test_trajectory_drop_past_threshold_fails_even_when_quality_improves` exists as a dedicated, hand-built test: the real live demonstration and the specific case the design was built for turned out to be two different tests, and both were needed to show the gate actually works end-to-end *and* actually needs both metrics.

Deliberately not built: per-case regression detection (which *specific* case regressed, not just the aggregate rate) — the spec asks for "configurable regression thresholds" on evaluation as a whole, and per-case baseline tracking for a 39-case dataset would need either 39 stored baselines or a more complex diffing scheme; the two-metric aggregate gate is the scoped version of what the spec actually asks for, and `data/evaluation/results/latest.json`'s full per-case detail is still available for manual inspection when a gate does fail. A GitHub Actions / CI-platform workflow file — the spec asks to "demonstrate how AI evaluation *could become* a CI quality gate," which `make eval-ci`'s exit code already does (any CI runner can gate on it); wiring an actual `.github/workflows/` file is a deployment concern, not something this local-first educational project has needed elsewhere either (there's no existing CI config in this repo to extend). Threshold values tuned per-metric-per-query-class — the two thresholds are dataset-wide, not per query class; the spec doesn't ask for that granularity, and 39 cases across 20 query classes is too small a sample for per-class thresholds to be statistically meaningful anyway.

## Milestone 18 — Optional Travel AI Search integration

**Goal**: introduce `TravelAISearchAPIProvider` — the Concierge may use a separately running Travel AI Search backend as one of its tools, demonstrating service composition without creating a hard dependency, and produce the trace shape the spec's own diagram names explicitly (`Concierge agent → search tool → Travel AI Search API → results → agent`).

**The design decision was already made — by ADR-003, three milestones ago.** The spec names the exact shape it wants: `TravelSearchProvider` with `LocalSyntheticTravelSearchProvider`/`TravelAISearchAPIProvider` implementations. That is `LLMProvider` (Mock/Anthropic) with different nouns. Rather than treat this as a new design problem, the actual work was checking whether the *reasons* ADR-003 chose a Protocol-based thin abstraction still applied here (they did — same "tests need an offline double," same "swapping backends shouldn't touch call sites") and finding the one place the two abstractions genuinely need to differ, not rediscovering the pattern from scratch.

**What we chose and why**:

- **Deliberately synchronous, not `async def` like `LLMProvider`.** `agent/nodes.py`'s `tools_node` calls every `TOOL_REGISTRY` entry as a plain sync call (`func(**call.arguments)`, never awaited) — a convention every tool and every milestone since M4 depends on. Making `TravelSearchProvider` async would mean making `tools_node`, `TOOL_REGISTRY`, and the whole tool-execution path async too, a much larger and riskier change than a search-backend swap needs. `TravelAISearchAPIProvider` uses `httpx2.get(...)` (sync, module-level calls — matching the one other real outbound HTTP call site in this repo, the Chat UI's own `httpx2.post(...)`), not `AsyncClient`. Full reasoning in [ADR-006](decisions/ADR-006-travel-search-provider-abstraction.md).
- **The Protocol's method signatures are identical to the tool functions' own signatures** (`tags`/`climate`/`limit`, `destination_id`/`family_friendly`/`max_price_band`/`limit`), not a generic "fetch raw data, filter here" split. A real search API is exactly the kind of thing that filters server-side — `LocalSyntheticTravelSearchProvider` filters this project's own static JSON in Python (the same logic that used to live directly in `tools/travel_tools.py`, moved unchanged); `TravelAISearchAPIProvider` forwards the same parameters as query params and trusts the response is already filtered, no client-side re-filtering. This is also *why* the refactor could be behavior-preserving: `tools/travel_tools.py`'s public functions keep the exact same signature and exact same default (local) behavior, so `test_travel_tools.py`'s 15 pre-existing tests needed zero changes and still pass.
- **Both providers open the same `travel_search_backend` span, nested inside the tool span** — not two differently-named observations. This is the direct, deliberate parallel to `MockProvider`/`AnthropicProvider` both opening `llm_call` (Milestones 2/5): the trace shape shouldn't depend on which concrete backend is configured, only `metadata.backend` should say which one actually served it. It also happens to be exactly what the spec's own diagram draws as a distinct step ("→ Travel AI Search API →"), and gives a genuine, isolated latency signal for the search backend — the spec's own "measure service latency independently from LLM latency" — for free, from the span's own duration, no hand-rolled timing needed.
- **The HTTP contract is designed, not confirmed, and said so explicitly rather than implied as fact.** This repo has no access to the real, separate Travel AI Search project. The three assumed endpoints (`GET /destinations`, `GET /hotels`, `GET /destinations/{id}`) and the assumption that response bodies validate against this project's own `Destination`/`Hotel` models are a best-effort design, matching the spec's own allowance ("the dataset may be compatible with or derived conceptually from the synthetic dataset used by the existing Travel AI Search project") — not a claim of having verified a real integration. `model_validate(...)` raising a clear error on a shape mismatch, rather than silently accepting malformed data, was a deliberate choice for the same honesty reason M5's Anthropic tool-call translation was pinned by real SDK introspection instead of assumption.
- **The integration test is NOT skip-by-default, unlike `test_anthropic_provider.py`.** `test_anthropic_provider.py` skips without a paid `ANTHROPIC_API_KEY` because a fresh clone genuinely can't get one for free. This milestone's integration test needs no external credential at all — only a loopback HTTP server, which the test file starts and stops itself (`http.server.ThreadingHTTPServer` on an OS-assigned port). There's no reason to make this optional when it costs nothing and needs nothing external; it runs, for real, every time `make test-integration` runs.
- **On a backend failure, no new error-handling code was written at all.** `TravelAISearchAPIProvider` lets a real HTTP error or connection failure propagate unhandled; `tools_node`'s existing per-call `try/except` (Milestone 6) already turns it into a graceful "tool" error message the agent's next turn can react to — the identical recovery path Milestone 15's `tool_exception` fault already exercises and tests. This directly closes a gap Milestone 15's own RATIONALE entry named and left open: *"'Travel provider error' has no real second provider to demonstrate a fallback *to* — this project has only ever had the local synthetic data source... that specific spec example isn't fully exercisable here yet."* It's exercisable now, and needed zero new code to be so — the M6 recovery mechanism was already general enough.

**A real circular import, found by running the tests, not anticipated in the design above**: `tools/travel_tools.py` needs `providers.travel_search` (for `get_travel_search_provider()`); the natural implementation of `LocalSyntheticTravelSearchProvider` needs `tools/data.py`'s JSON loader; but importing anything from the `tools` package first runs `tools/__init__.py`, which eagerly imports `travel_tools.py` — which needs `providers.travel_search` again, still mid-import. `pytest`'s collection error named the exact cycle precisely (`cannot import name 'get_travel_search_provider' from partially initialized module`), not a guess. Fixed by moving the loader to `providers/travel_search/data.py` — not a workaround, but the more architecturally honest placement anyway: loading the local dataset is a concern of the *local search provider*, not of the generic tool-wrapping layer that used to own it by historical accident (it was the only data source that existed when `tools/data.py` was written, back in Milestone 4, before there was a second provider to distinguish it from).

**Surprises worth carrying forward**: the strongest confirmation this abstraction was designed correctly wasn't a new test asserting something novel — it was every *pre-existing* `test_travel_tools.py` test passing completely unmodified after the refactor. A provider abstraction whose introduction requires touching the behavior (not just the implementation) of the code that already used the thing being abstracted is a sign the abstraction boundary was drawn in the wrong place; here it wasn't touched at all. The one real surprise was procedural, not architectural: the import cycle, which would have been easy to introduce silently in a codebase without a fast, comprehensive test suite already in place to catch it immediately on the very first `pytest` run.

Deliberately not built: `OpenAIProvider`-style parity with the LLM side isn't relevant here (there's no second real backend vendor to add for search, only the one named in the spec); automatic fallback from `travel_ai_search_api` to `local` on a failed request — the spec's own framing is "service composition without creating a hard dependency" (the app must still run on `local` alone), not automatic failover mid-request, which would need a policy for partial results and retry semantics the spec never asks for and this milestone didn't need to invent; a smoke-test script mirroring `fault_injection_lab.py`'s narrated-output style — the real, always-running integration test already gives live, verified evidence without a second, largely-duplicate code path to maintain.

## Milestone 19 — Langfuse Cloud

**Goal**: "Document and test optional Langfuse Cloud configuration. Switch through environment variables only. Verify that the same application can send traces either to local self-hosted Langfuse or Langfuse Cloud. Do not duplicate instrumentation code."

**The first, and largest, finding: there was nothing left to build.** Before writing anything, I re-read `observability/langfuse_client.py` — `get_langfuse_client()` has exactly one line touching the host, `host=settings.langfuse_host`, with zero conditionals on its value, unchanged since Milestone 1. ADR-004 already made this exact decision back then ("Option C — self-hosted default, Cloud as optional override... No code changes required to switch"); README and `.env.example` already carried the three-line switch instructions. A grep across `src/`/`ui/`/`scripts/` for `localhost:3000` or `cloud.langfuse.com` found exactly one hit — the `Settings` default itself, which is supposed to be there. "Do not duplicate instrumentation code" was already satisfied, by a decision made 18 milestones ago. The actual gap was the word "test" in the spec's own sentence: nothing had ever *proven* the switch worked, only asserted it.

**What we chose and why**:

- **No new abstraction, no new provider, no new module.** Every other recent milestone (16-18) added a real mechanism (a bug fix, a regression gate, a provider abstraction). This one adds tests and documentation on top of a mechanism that already existed — resisting the temptation to invent something to build was itself the right call here, not a shortcut. Writing new code to "make Milestone 19 feel substantial" would have been solving a problem that didn't exist, at the cost of a change with real regression risk to a code path every single request goes through.
- **`tests/integration/test_langfuse_connectivity.py` was reframed, not duplicated.** The instinct to write a *new* `test_langfuse_cloud.py` file with its own separately-configured `Langfuse(host="https://cloud.langfuse.com", ...)` client was rejected deliberately: that would mean two code paths constructing a Langfuse client for two purposes that are actually the same purpose, exactly the "duplicate instrumentation" the spec says not to build. Instead, the *existing* connectivity tests already exercise `get_langfuse_client()` — the one, real, production client-construction path — so reframing their docstring to make explicit "these tests verify whichever target `Settings` currently names" turns already-passing tests into the Cloud verification mechanism, with a one-line diff.
- **One new assertion closes the loop between "configured" and "actually happened."** `test_can_create_and_flush_a_trace_and_it_lands_at_the_configured_host` now asserts `trace_url.startswith(get_settings().langfuse_host)` — proving a real trace landed at the *actual configured* host, not just that *some* trace URL came back (which the old assertion, `trace_id in trace_url`, would pass even if the URL pointed somewhere else entirely by accident). This is the one gap the pre-existing test genuinely had.
- **One new offline unit test pins the part that doesn't need real network at all**: `test_construction_does_not_raise_with_a_cloud_shaped_host` proves `get_langfuse_client()` builds successfully for a Cloud-shaped host, exactly as uneventfully as a local one — construction performs no I/O (established since M1), so this is fully offline and fully deterministic. It deliberately does **not** inspect `client._base_url` or any other SDK internal — `test_langfuse_client.py`'s own docstring already states that principle ("we deliberately do not assert on the SDK's internal attributes — only on behaviour our own code is responsible for"), predating this milestone; respecting an existing file's stated testing philosophy mattered more here than a marginally stronger assertion would have.
- **Real evidence used what was actually available, not what would have been ideal.** This environment has no Langfuse Cloud account — the same "no credential here" gap as the Anthropic and real-judge integration tests, stated plainly rather than worked around. What *is* real: this environment's own `.env` already points at a non-default host (`http://localhost:3001`, not `3000` — an actual port conflict from Milestone 1), and the reframed test suite passes against it, with the new assertion confirming the returned trace URL matches that exact non-default host. That's genuine, unstaged evidence the mechanism generalizes past the one value everyone's `.env` happens to share, even without a real Cloud round-trip to point to.

**Surprises worth carrying forward**: this is the first milestone in this project where "inspect the current implementation" concluded "the implementation is already correct and complete; the work is proving and documenting that, not changing it." Every milestone before this one found at least one real gap to close in the *application* code. Recognizing that pattern didn't apply here — and resisting inventing one to force a bigger diff — is itself worth naming as a distinct kind of engineering judgment from the fifteen-odd "found and fixed a real bug" stories in the milestones before it.

Deliberately not built: a separate Cloud-only credential pair (e.g. `LANGFUSE_CLOUD_PUBLIC_KEY`) distinct from `Settings.langfuse_public_key`/`_secret_key`, which would have let local and Cloud tests run side by side in one invocation without touching `.env` — rejected because it would itself duplicate the one credential concept `Settings` already models, purely for test convenience; a real live round-trip against Langfuse Cloud — no account is configured in this environment, and fabricating a result was never on the table. A CI-matrix running against both targets automatically — this repo has no existing CI configuration to extend (the same reasoning Milestone 17's "deliberately not built" list already gave for its own CI-platform question).

## Milestone 20 — Production observability architecture

**Goal**: "Document how the educational system would evolve in production... Do not necessarily implement all of this infrastructure. The goal is architectural understanding" — twelve named topics: Langfuse, API metrics, logs, distributed tracing, OpenTelemetry, Prometheus/Grafana or cloud APM, alerting, trace sampling, data retention, PII, secrets, scaling, high availability, asynchronous ingestion, multi-region.

**The spec itself settled the scope question before any writing started.** Every prior milestone in this project (M0-M19) added or verified real code. This one explicitly asks for the opposite: understanding, not infrastructure. The temptation to "make the milestone feel substantial" by building a toy Prometheus exporter or a stub OTel Collector config was real and was rejected for the same reason Milestone 19 rejected inventing a new abstraction where none was needed — building something the spec doesn't ask for isn't rigor, it's scope creep dressed up as thoroughness.

**What we chose and why**:

- **`docs/PRODUCTION_ARCHITECTURE.md` is grounded in this specific codebase, not written as generic cloud-architecture advice.** Before writing a single topic section, I verified concrete facts about the current system rather than assuming them: grepped for every `logger.info`/`.warning`/`.error` call in `src/` (found exactly two — startup and shutdown), checked whether `structlog.contextvars.bind_contextvars` is called anywhere (it isn't, even though `merge_contextvars` is already wired into the processor chain), grepped every route file for an auth dependency (found none), and read `ConversationStore`'s actual docstring rather than trusting a paraphrase of it from memory. A document that says "your logs and traces can't be correlated because nothing binds `trace_id` into the logging context" is a materially different, more useful claim than "add structured logging with correlation IDs" — the same specificity this project's own `RATIONALE_PER_MILESTONE.md` entries have held themselves to since Milestone 1.
- **A real accuracy bug was caught and fixed before this document even shipped**: an early draft attributed a paraphrased sentence to `ConversationStore`'s "own docstring" in quotation marks, as if quoted verbatim — it was actually `CLAUDE.md`'s summary of the docstring, not the docstring's real text. Reading the actual source (`conversation/store.py`) turned up the real wording ("semi-durable... durable enough to give the agent real multi-turn memory... but gone on restart") and the quote was corrected before publishing. Worth naming explicitly: even a pure-documentation milestone with no code changes can ship a real, checkable error, and the same "verify before quoting" discipline this project applies to SDK internals applies to its own prior documentation too.
- **A "what's already production-shaped vs. deliberate shortcut" table opens the document**, before any of the twelve topics — so the rest of the document argues from an accurate baseline (async ingestion already works; conversation memory is single-process; auth doesn't exist at all) instead of reading like every topic is an equal-sized gap. Some aren't gaps at all — Langfuse's async batch export (M1, proven live in M15's unreachable-host test) needed no changes to become production-shaped; it already is.
- **The twelve topics are explicitly ranked by launch-blocking urgency at the end**, not left as an undifferentiated list. Secrets/auth and PII/retention are framed as launch blockers; multi-region and a general OTel Collector are framed as explicitly *not* needed until a second real service or a second region exists — naming that distinction is itself the "architectural understanding" the spec's own closing line asks for, not just an inventory of concerns.
- **One topic not in the spec's own list — authentication — is named anyway**, briefly, under the [Secrets](PRODUCTION_ARCHITECTURE.md#secrets) section, because it's true and material (there is genuinely zero auth on any route today) and omitting a real, verified finding to stay strictly inside the spec's literal twelve-item list would be a worse choice than a two-sentence aside.

**Surprises worth carrying forward**: the `structlog.contextvars.merge_contextvars` finding was the most useful single discovery in this milestone — the correlation mechanism between logs and traces isn't *missing* infrastructure, it's *unfinished* infrastructure: the processor is already wired, and the one missing piece is a single `bind_contextvars(trace_id=..., session_id=...)` call at the top of `chat.py`'s request handler. That's a genuinely different, more actionable finding than "add log/trace correlation" would have been, and it only surfaced by reading the actual processor chain in `logging_config.py` instead of assuming the gap was total.

Deliberately not built: any of the twelve infrastructure pieces themselves (a real Prometheus exporter, an OTel Collector config, a PII-masking function, a Redis-backed conversation store) — the spec's own instruction is explicit that this milestone is documentation, not implementation; building any one of these for real would also mean picking a specific vendor/tool (which Prometheus remote-write target, which secrets manager, which APM) that this educational, infrastructure-agnostic project has never needed to commit to for anything else. No new tests — there is no new production code for tests to cover; `make check`/`make test`/`make test-integration` were re-run afterward purely as a zero-risk sanity check that a documentation-only change didn't somehow break anything, and they didn't.

## Milestone 21 — Final experiment suite

**Goal**: "Create a representative experiment matrix... Report: deterministic score, LLM judge score, human feedback where available, tool accuracy, groundedness, latency, cost. Produce a final engineering analysis: which configuration should we deploy, and why?"

**Every required report dimension already had a real mechanism before this milestone started — the actual job was composing them, not building a seventh.** Deterministic score is Layer 1 (M9). LLM judge score is `evaluation/judge.py` (M11). Human feedback is `POST /feedback`'s real Langfuse score (M12). Tool accuracy and groundedness both live inside `evaluation/trajectory.py`/`evaluators.py` (M9/M13). Latency and cost are `evaluation/cost_latency.py` (M14). This inventory — checking what already exists before writing anything — is the same discipline Milestone 19 applied to the Langfuse Cloud switch and Milestone 20 applied to production architecture; it's becoming this project's default first move for any new milestone, not a one-off.

**What we chose and why**:

- **The spec's own example matrix (prompt version x two models x tool descriptions) was substituted, honestly, with the two axes that are actually live under `LLM_PROVIDER=mock` in this environment.** A second real model needs `ANTHROPIC_API_KEY`, unavailable here — the same recurring gap as every prior real-provider milestone. Rather than build an inert matrix that would technically satisfy the letter of the spec's example while measuring nothing real, the 4-config matrix crosses `PROMPT_LABEL` (the spec's own "prompt version" axis, genuinely exercised) against `AGENT_MAX_ITERATIONS` (Milestone 14/17's own already-proven-to-differentiate axis, standing in for "model" as the second real, live dimension). The script's own docstring states this substitution and its reason plainly, and shows the one-line change (`env={"LLM_PROVIDER": "anthropic", ...}`) that would restore the spec's literal matrix the moment credentials exist.
- **A real bug was found before the suite ran even once, by reading the function being reused rather than assuming it would just work**: `run_case_with_metrics()` (M14) hardcodes `extra_tags=["cost-latency-experiment", config_name]`. Reusing it unchanged for this milestone would have tagged every M21 trace as if it were an M14 trace — accurate code reuse, inaccurate observability. Fixed with a backward-compatible `experiment_tag` keyword parameter (default unchanged, M14's own 12 tests needed no edits) rather than either duplicating the function's provider-patching logic for a second time or leaving the mislabeling in place. Verified live, not just by argument: opened a real trace afterward and read its actual tags.
- **`ConfigSuiteResult`/`run_config_suite()` is pure aggregation, no I/O** — the same "pure logic, separate from the async runner" split `compute_config_metrics()` (M14) and `check_regression()` (M17) already established, specifically so the composition logic is unit-testable with hand-built fixtures (`tests/unit/test_final_suite.py`, 12 tests) instead of needing a real 39-case run for every test case.
- **The groundedness proxy is isolated to its own single-evaluator pass rate**, not reused wholesale from `compute_quality_metrics()`'s all-five-evaluator aggregate — the spec's report list asks for "groundedness" as its own line item, not folded into a combined quality score that already exists elsewhere in the same report.
- **The final analysis's ranking key deliberately reuses Milestone 17's own two-metric philosophy** (`quality_pass_rate`, `trajectory_healthy_rate`) rather than inventing a third scoring scheme — the same reasoning M17 already applied when it rejected a single blended score after Milestone 16 showed the two metrics can move in opposite directions.

**A real methodological validation, not a coincidence**: the 4-config matrix produced exactly two behavioral clusters — the two prompt-version pairs matched to two decimal places on every metric (`providers/llm/mock.py`'s `_decide()` never reads the system prompt, confirmed by reading the function, not assumed), while `AGENT_MAX_ITERATIONS` produced the same large, consistent gap Milestone 14 already found (73.1%→54.2% quality, 43.6%→2.6% trajectory health). A harness that produces identical numbers for two configs known in advance to be behaviorally identical, and a large, consistent gap for two configs known in advance to differ, has passed a real validity check — the opposite result (four different numbers, or four identical ones) would have meant something was wrong with the measurement, not the configs. `prod-v1 x multi-step`'s `quality_pass_rate` additionally matched Milestone 17's committed baseline to the full floating-point digit — an independent cross-check that this newly-built composition layer measures the same thing the existing regression gate does, found by comparing numbers after the run, not planned as a test in advance.

**The auto-generated analysis was written to avoid a specific, foreseeable failure mode**: with two configs tied exactly, a naive "sort all four, print the top one" implementation could read as recommending `prod-v1` over `staging-v2` from nothing but floating-point noise in a tie. `render_final_analysis()`'s explicit caveat paragraph states the Mock-invariance fact directly, so the report can't be misread as a real prompt-quality finding — a small design decision, but the kind of thing an auto-generated "engineering recommendation" needs to get right, since the entire point of automating the analysis is that nobody will necessarily eyeball the raw numbers before acting on the conclusion.

**Surprises worth carrying forward**: the strongest evidence this milestone's new code is correct wasn't a new assertion invented for the occasion — it was three independently-known-in-advance facts (prompt invariance under Mock, the `AGENT_MAX_ITERATIONS` gap from M14, and M17's committed baseline number) all reproducing exactly through a measurement path that had never been exercised in this combination before. Composing already-tested pieces and having the composition validate itself against prior, independently-derived results is a stronger signal than any unit test written in advance could have provided, precisely because nobody wrote those expected numbers down as assertions beforehand — they were simply what the existing project already knew to be true.

Deliberately not built: a real second-model comparison and an "improved tool descriptions" variant — both would be inert under `LLM_PROVIDER=mock` for the same structural reason the prompt-version axis is (`MockProvider` reads neither prompt content nor tool descriptions, only tool *names* and the last user message), so building either would only prove the same fact a second and third time rather than add information; a `--push-to-langfuse` flag mirroring Milestone 14's own — that mechanism was already thoroughly demonstrated in M14's entry, and pushing 4 configs x 39 cases as a second, largely duplicate Langfuse Experiment run here would add trace volume without new insight beyond what M14 already proved works.
